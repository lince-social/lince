# Ontology

## Ordering

The Facade and the Resenha-gated scenarios go last. They are not blocked on each other and not blocked on anything here; they are last by choice, so nothing else in this document may be planned as depending on either. Concretely that is T2 the Facade, the public face of an Organ, and Deployments — whose items are Resenha scenarios rather than chores.

T0 and T1 of the Organ Profile are not part of that deferral. The announcement and the card are their own tier, cut by size, and a card carries its own consent and signature questions that have nothing to do with a Facade. Only T2 waits.

Everything else — the cleanups, Visibility, devices and identity, discovery and gossip, Relay Cells, and cluster 4 — is ahead of both.

## The surface debts live in the interface plan

Eleven items whose mechanism is built and shipping, and whose only missing half is a way for a person to reach it, live in `anicca/interface/plans/interface.md` under "Ontology surfaces this interface owes" — the plan that owns the thing that will draw them. They are not deferred and not deleted; they sit where the work happens, so this document stops listing UI it cannot schedule.

What went: the contact-visibility summary; per-device sharing limits; the per-Cell capability editor; the succession chain; a reach control per contact; a Move button; the rate-limit line; "no device list yet — reconnect to finish"; one pending-offers list; a Trash and Restore; the read-model health line.

What stayed here is only what still needs backend work, plus the discovery, gossip and relay design.

## Decisions — landed or refused, do not re-add

**One name for one act: `create-message`.** `Action::SendMessage` is gone. `create-message` was the superset — it carries `parent` and `references`, tolerates a thread with no replica root, and runs the transfer-thread writer check — and both actions already sat in the same permission arm, so collapsing them changed no permission. `Action::CreateMessage` and `threads::send_message` both still exist, the latter used by the thread-invite path and by the `individual_replica` and `live_workflow` tests.

**`file_sync.rs` no longer claims selection is unconfigurable.** The module doc said "Selection is deliberately NOT Protein-configurable yet" forty lines above `configured_filter`, which deserializes a `protein::Predicate` out of the sync config. Replaced with what the code does (`crates/engine/src/file_sync.rs:9`).

**The per-Cell surface config no longer lives on a Record that syncs.** This was the worst finding of the audit: not unbuilt, but attempted and undone by live code. Migration `0067_no_base_url.sql` blanked the Organ Record's body and deleted every `lince.organ` extension row — and `store::organs::ensure_local` wrote both straight back on every boot, with `adopt_identity` writing the same blob raw during enrolment. The migration cleaned a table the next process refilled, so the list read as though this had landed while one device's `baseUrl` still travelled to every sibling Cell.

`baseUrl`, `aliases` and `local` now live on the Cell Record under `lince.cell.surface` (`store/src/organs.rs:15`), which never syncs and never logs an op — the reason `cells.rs` already documents, and the same reason a relay holding `relay_capabilities()` can still configure itself. `crates/store/migrations/0072_surface_config_on_cell.sql` is a new migration rather than an edit to `0067` in place, against the usual rule for unshipped migrations, because `0067` had already run on the dev database and editing it would have been a no-op there. The empty-string contract is preserved exactly: `ensure_local(pool, "")` still means "do not change the address", so a CLI invocation cannot wipe the address a running web Cell wrote. The regression guard is the negative assertion in `crates/engine/tests/organ_cell_split.rs` — reading the surface back proves nothing, and what matters is that the syncing Record carries no surface to travel with, which is what `this_cells_address_never_reaches_the_organ_record` and `joining_an_organ_keeps_the_address_on_the_device` assert. Both would have failed against the previous code.

**Tree sync and the Move verb are built.** `Action::MoveRecordTo` and `Action::CancelRecordMove` (`actions.rs:404,409`, arms at `3536`), `store/src/record_move.rs` over migration `0070_record_move.sql`, the exactly-once hand-over in `engine/src/share.rs` (`still_queued` → `last_op_seq` → `mark_handed_over`), and `engine/tests/contact_share.rs:631` covering a moved Record carrying its children. The dangerous half — Move as distinct from Copy, where delivering twice means two copies and losing the ack destroys data — is the half that exists. What is missing is only a way to reach it, and that is in the interface plan.

**Replica bootstrap for a new contact is refused, not pending.** `crates/engine/tests/replica_bootstrap.rs` argues it in its own header: retention only drops ops that a newer op for the same target superseded, so the surviving log always contains, for every live field, the op that established its current value — "bootstrap" is replaying from zero and is complete by construction. The snapshot alternative was rejected because it needs synthesized `(actor_cell, hlc)` identities, and that identity is the unique index the import path dedupes on.

**`contact.mode` is load-bearing, not unused.** The column was repurposed: `Contact::reach()` maps it to `direct` / `mailbox` / `auto`, migration `0066_contact_reach.sql` normalised it, and `engine/src/wire.rs` branches on it to decide mailbox versus direct delivery. What is genuinely missing is that nothing sets it — `store::organs::set_mode` still has exactly one caller and it is `engine/tests/contact_reach.rs:183`. The surviving half is a reach control on the contact panel, and it is in the interface plan.

**`Engine::cell_may` is called.** `wire.rs:1828` calls it with `CAP_REPRESENT`. What is missing is only the capability editor, which is in the interface plan.

**The absent-not-blank sweep is not a backend item.** It was deleted as a cleanup entry and survives as a rule the interface refactor must adopt. `Protein.fields` is set to anything but `None` only in engine tests and in the new interface crate itself (`interface/src/spatial_diagnostic.rs:551`, `interface/src/domain.rs:765`), the sands are being rebuilt right now, and a sweep of `row.body || ""` across sands about to be replaced is a large diff thrown away on landing. The rule belongs in the new renderer's contract, stated once: `undefined` renders as "withheld", `""` renders as empty. A sand that draws a missing `assignee` as unassigned draws a permission boundary as data.

**Undelete does not need a new lifecycle op.** The undelete rule already exists and already works: "undelete is a newer write" is enforced on the import path today, where `sync.rs` compares a `set` against the latest tombstone and passes `undelete: true`, and `sync_apply::undelete_record` clears `deleted_at`. A restored Record's Loro doc is not destroyed by the tombstone either; its ops stay in the log and the doc is merely refused new updates while the tombstone is the latest word. Adding a second lifecycle layer above the tombstone would buy nothing. What is actually missing is a local Action that emits such a write and a Trash to pick from, and neither is a lifecycle op.

**The Deployments scenarios are Resenha scenarios, not deployment chores.** They are the Ontology features that cannot be proved by one Cell on one machine, and Resenha is the thing that runs many Lince and simulates time, network and disk. So they go to Resenha as named, seeded, asserted runs — not as "set up a VPS". The condition that matters is that each one states its seed, what it does, and what it asserts; a scenario that says "check sync works" proves nothing, and the scenarios are what will make these features testable at all, so vagueness in them is the whole failure. The Resenha chapter exists again in `Lince.lingua` but is written as the multi-Lince TUI plus DST and does not contain these scenarios; where they land is the owner's call.

**Naming links in a scope.** The scope language was column names only, and `record_assertion` is a relationship between Records, which no column name can say — so `op_in_scope` answered `false` for every assertion and `false` for every concept, and a narrowed contact received the whole graph stripped out. The vocabulary extension is a prefix, not a reserved word in the column list: an entry beginning `link:` names links and can never collide with a column, because a column name has no colon. `link:*` is every link; `link:part-of` is only that predicate's. `store::sync_ops::LinkScope` carries the resolved form and `resolve_link_scope` turns the human names into predicate uids once per pass rather than once per op.

Four decisions inside it, each with a test in `store/tests/scope.rs`. A scope naming no link still receives none — fail-closed is unchanged, and what changed is that there is now a way to ask. A retraction rides whenever any link does, because an assertion tombstone carries no predicate in its value and so cannot be matched by name, and withholding it would leave a narrowed contact holding a link forever — the same shape as the record-tombstone exemption, for the same reason. The predicate Concept rides with the links that need it, because a link whose predicate has no name is unreadable, which is why `upsert_assertion` already stubs one on the way in; a scope wanting no links still gets no concepts. A link whose value carries no `predicate_uid` stays home under a by-name scope.

`op_in_scope` keeps its cheap four-argument signature for the two engine callers that have no op value in hand — the inbound accept gate and the outbox drop check — where it now reads "any link named" and lets serve-time narrowing be the authority. That is the correct direction for both: the accept side errs toward keeping data, and the outbox side only decides whether to keep a row queued.

**The read half of per-person permissions.** Permissions gated create, update and delete; anyone with a login saw every Record. `organ:read` already existed as a permission key in `utils::auth::ALL_PERMISSIONS` and no Action used it, so the old note was wrong about the key and right about the effect; seven pure reads — `RosterStatus`, `MailboxStatus`, `MailboxPickupPoints`, `MailboxOutbound`, `MailboxRequests`, `FileSyncStatus`, `AuditContact` — moved off `organ:update` and onto it. Admin holds both, so nothing narrowed; what it buys is a role that may look without being able to change. One saved Protein predicate per login lives in `person_credential.read_filter` under migration `0075`, set by `Action::SetPersonReadFilter` under `user:update`, and NULL is unnarrowed and is the default — not the same as an empty predicate, which is a real and different answer.

The filter is evaluated on the scoped read and mapped Action-target paths. `protein::execute_for_with_context` intersects it into the visible allowlist, and `act_at_inner` checks targets enumerated by `read_filter::record_targets_of`; `engine/tests/read_filter.rs` covers a refused Record text edit. This is not complete company-policy coverage: some Protein sources do not receive that allowlist, collaborative text has another visibility path, and the target enumeration is partial. [Backend Part A B05–B08](backend-part-A.md) owns closing and proving those paths before private company use. A filter that only hides things on screen is a display preference, not a boundary.

**The comment rule is enforced everywhere.** The strip itself was already done; what was missing was the gate, because `sensei::teach` was called from one `build.rs`. Every crate calls it now — `store`, `engine`, `nucleus`, `protein`, `transport`, `web`, `lince`, `lince-utils`, `desktop`, `lince-interface`, `lince-fiote`, `anicca` — and it was proven rather than assumed: adding a single `//` to `store` fails the build with the file and line. `NoComments` scans `.rs` under `src/`, `tests/`, `benches/`, `examples/` and `build.rs`; the sands' `.js` and `.html` are outside it and are being replaced anyway.

**One backoff implementation, and it is not the sync outbox's.** `store::backoff` is the single exponential calculator and `transfer_delivery::outbox_mark_failed` computes its wait through it, with unit tests over the base delay, the doubling, the ceiling holding against `i64::MAX` attempts, and an unreadable stamp being read as due rather than stranding a row forever. Adding `next_attempt_at` to `sync_outbox` was built and reverted the same day: it broke four tests, all the same scenario, where a peer goes offline, comes back, and the message is supposed to arrive and did not because the ops were no longer due.

The two schedulers back off different things, and that is why they are not one policy. `transfer_delivery_outbox` backs off an envelope to a person — per row, retried on its own clock, and a wait there is correct. `sync_outbox` is a queue of ops for a contact, drained per contact, and its retry cadence is the sync pass. What should back off on that side is dialing an unreachable Cell, which is a different object from the ops waiting to go; putting the delay on the queue meant a peer that reconnected instantly still waited. The unification is real for the calculation and false for the policy, and if the sync side ever gets a backoff it belongs on the dial, beside `unreachable_since`, not on the rows.

**The per-contact predicate on the feed was already built.** The per-contact predicate is `organ_contact.share_protein`, per-Record evaluation on the serve path is `engine/src/share.rs`, and the served-set table is `contact_share` under migration `0064`, whose `picked` and `held` columns are exactly "matches the rule now" versus "they actually hold it" — `share.rs:130-131` computes `entered` and `left` by differencing against the stored `picked` set, and that difference is the crossing detection the entry called the whole point. `engine/tests/contact_share.rs` covers entering, leaving, returning, and a Record deleted after it left. What is not built is the surface the entry demanded before switching it on: a Record entering is a grant and one leaving is a revoke, both fired by an edit nobody meant as an act of sharing, so "what are you sharing right now" has to be answerable first. That is a question for the interface plan, not backend work.

**A refusal you remember, that the sender cannot detect.** The blocking question was whether a refusal should be remembered per kind, and the answer is yes for all four, because the question contained a conflation that was doing real damage. What the sender learns must be identical for declined and ignored — that is a genuine rule, because the difference between them is a probe, and a stranger who can tell them apart can map who is reading their offers. What I remember locally is nobody's business but mine. Destroying my own memory to protect the sender's ignorance protected nothing and cost something real: a stranger whose invite I declined could invite me again immediately, and again, and I would be prompted every single time. The anti-spam hole was wearing the privacy rule as a disguise.

`offer_refusal` under migration `0076` is local, never synced, never logged as an op — the same treatment `thread_invite` already gets, for the same reason. It is keyed `(kind, subject_uid, other_party)`, so refusing one party says nothing about another and refusing a conversation is not refusing a transfer, and all four kinds record one: `decline_invite`, `DeclineGrant`, `CancelRecordMove` and `RejectTransferInvitation`. The sender-facing answer is unchanged and that is the load-bearing part: `OfferGrant` already answered `Applied { applied: 0 }` whether the invite was stored or dropped as a duplicate, so absorbing a re-offer under a standing refusal returns the same value on the same path and nothing new is disclosed.

A refusal is a window, not a wall. `REFUSAL_WINDOW_DAYS = 30`, after which a fresh offer gets through, and `forget_refusal` lifts one by hand — a refusal that never expired would turn one bad moment into a life sentence, and people change their minds, and so do circumstances. `offers::pending` carries `previously_refused` per row, so the pending-offers list can say "you declined this before" rather than presenting a repeat offer as if it were new. `store/tests/offer_refusal.rs` covers the window standing, per-kind and per-party isolation, refusing twice moving the window rather than stacking, and an expired refusal no longer standing.

**The cross-process import guard.** The materialise step carries its own condition. `store::sync_apply::Stamp` is the op as the log identifies it (`tbl`, `uid`, `field`, `hlc`), and every applier writes only while no op with a higher `hlc` for the same target is already in `sync_op`. Single statements carry it as ` AND NOT EXISTS (SELECT 1 FROM sync_op WHERE tbl = ? AND uid = ? AND field = ? AND hlc > ?)`; the read-modify-write appliers — extension keys, assertions, concepts, and the quantity add — run the same check as the first statement inside a `write_tx` (`BEGIN IMMEDIATE`), so it is atomic with the write rather than a memory of one.

Re-reading the log's max after appending looks sufficient and is not: two processes can each see themselves as the winner and still execute their UPDATEs in the wrong order, so the condition has to be inside the writing statement. This does not contradict `Engine::import_lock`'s doc — what that rejected as "a large refactor" was a transaction spanning the whole import sequence across `store::sync_apply`, the Loro registry and an async boundary, and wrapping one applier's own RMW is not that. It weighs one `idx_sync_op_target` probe per applied op, with no new table, no new column and no extra write, and `sync_apply` is the remote path only, so the local write path is untouched. Rebuild gets it for free and is better for it: `rebuild` replays in `seq` order, which is not `hlc` order, so it could itself land the loser, and under the guard only the HLC winner writes and replay becomes order-independent — the `replayed` count therefore falls to the number of ops that actually changed the read model, and `engine/tests/rebuild.rs` asserts `> 0`, which still holds. The guard is `crates/engine/tests/stale_materialise.rs`, which materialises the loser after the winner is already in the log and asserts the read model keeps the winner and `audit_read_model` stays clean.

**Per-contact rate limiting on the reject path.** `store::contact_rate` with migration `0073_contact_rate.sql`, two allowances per contact, both rolling hourly: 200 refusals and 4 whole-log serves. `store::organs::quarantine` spends a refusal — the single choke point where we have done the work of refusing — and `import_ops` checks the backoff before anything else, so a contact past its allowance is refused before the parse rather than after it. `FetchOpsSince` with an empty vector is the "send me everything" case and spends a serve. `states()` is what the contact panel renders and `clear()` lifts a backoff by hand. `quarantine_tally`, created by `0065`, seeded once and maintained by no code — a lifetime count frozen at that migration — is dropped by the same migration.

**Two enums named `Reach`.** `store::organs::Reach` became `Delivery` and `Contact::reach()` became `Contact::delivery()`; `engine::wire::Reach` keeps the name. Three call sites, no wire string changed — the column still stores `direct`, `mailbox` and `auto`.

**A mention in a body becomes a link.** `engine::body_links`, with the rule where the item put it: on the generator, never the parser. `link_first_mentions` rewrites the first whole-word mention of each other selected Record's head into `[[Title|uid]]` and leaves every later mention plain; longer titles win an overlap, a Record never links to itself, and text already inside a `[[…]]` is never touched and counts as that Record's mention. `file_sync`'s `.lingua` render calls it. `mentions()` reads links back with the uid authoritative and the title decoration, and `check_body_links` refuses a body link pointing at no Record — the same rule the prelude already followed, for the same reason. Renaming a Record still rewrites nobody's body. A bare `[[Project A]]` is parsed and left alone rather than resolved, because resolving by title is the retargeting the format exists to prevent.

**Exact multiply and divide was already built, to the letter of the spec.** `DecimalValue::mul_exact`, `div_exact` and `mul_ratio` with `Rounding` and `RoundedDecimal` (`nucleus/src/karma/value.rs`) route every inexact operation through one `round_ratio`; publish-time refusal is `infer_exact_product` in `karma/proof.rs`, where no declared scale or a scale over `MAX_DECIMAL_SCALE` refuses the Program; the zero divisor is a runtime `DivisionByZero` in `karma/evaluate.rs`; and unit algebra is explicit — scaling by a plain decimal keeps its own unit and refuses a declared one, while two dimensioned operands must declare the result unit or declare it dimensionless, so nothing ever invents `kg²` or silently drops a dimension.

**The read model is audited on a schedule.** `audit_and_repair` existed and ran nowhere but a test; `Engine::audit_read_model_if_due` now runs from the heartbeat every six hours, on its own cadence rather than the beat's because it walks every field tip. The clock is wall-clock and persisted, not a counter in memory: a Cell restarted more often than the period would otherwise audit on every boot, and one left running for a week would audit once. The outcome lands in `lince.cell.read_model_audit` on the Cell Record — never syncs, never logs an op, the same home and the same reason as the surface config — as `ReadModelHealth { at, checked, diverged, repaired, replayed }`, and a divergence also warns in the log. `read_model_health()` returning `None` means no pass has run yet, which a panel must not draw as a tick.

**The no-roster gap, closed as far as it honestly can be.** Both halves the fix needed turned out to be built already — pairing fetches the roster in the same breath as the introduction (`wire.rs:1298`) and `pull_catch_up` refreshes it on every connection (`refresh_roster`, `wire.rs:4040`) — so the gate can refuse. But refusing outright is wrong and the tree proves it: it broke 20 tests across `contact_share`, `collab` and `individual_replica`, every one a contact added without a wire pairing, which is a legitimate path (pasting a public value) and not only a test convenience. A peer mid-first-boot has no roster to give either.

So the gate is a grace window, not a switch. The first batch from an Organ we hold no roster for sets `awaiting_roster_since` under migration `0074`; the batch is admitted under the existing floor while the sync pass keeps asking; and after `ROSTER_GRACE_DAYS` of 7 the batch is refused with a reason a person can act on. Adopting a roster clears the marker, wherever it came from (`store_roster`). The floor in `inadmissible`'s no-roster branch is now the local Organ's, plus contacts still inside their grace window. What the grace window buys is honesty, not safety: dedup poisoning stays open against a contact for its first week, the alternative was refusing legitimate traffic, and a silent admission was worse than either — the marker is what lets the contact panel say "no device list yet — reconnect to finish" instead of the sync merely looking broken.

**One pending-offers list, read side.** `store::offers::pending` presents all four handshakes in one vocabulary — kind, direction, subject, title, other party, when — over the four existing tables `invites`, `replica_grant`, `record_move` and `transfer_invitation`. It moves no writer and changes no delivery semantics.

**Live Box sessions belong to the interface plan.** Company live Record/task access now belongs to [Dogfeeding](backend-part-A.md) and does not wait for shared Box layout. `anicca/interface/plans/interface.md` owns the later Box session and specifies more than the Ontology entry asked for: a distinct versioned workspace protocol for hello, permission, snapshot hash and chunks, ordered transaction tail, editor intent, accepted canonical transaction or structured refusal, durable spatial-checkpoint batch, ephemeral preview and presence, gap recovery, access loss and host end, plus a guest caching a verified snapshot for quick reconnect, an explicit read-only unavailable-host view, and a human surface with connected, synchronizing, caught-up, offline, host-ended and access-lost states.

Two facts from the audit that plan should inherit, because they say what is not reusable. `transport::Session` holds nothing across a socket: it is constructed per connection with its `subscriptions` and `last_ephemeral` as plain `HashMap`s (`transport/src/session.rs:26-53`), and the `session_id` at `session.rs:112` is read off the auth session, so the new host state cannot be layered on it and has to be a durable thing of its own. And `session_id` already travels on the wire (`transport/src/protocol.rs`) while `board/transport.js` already reconnects with backoff and replays — the client half of the old protocol exists, but the new workspace protocol is versioned separately and fails closed on unknown versions, so it inherits none of it except the lesson.

**Reaching a Cell's own interface through a browser is not planned indefinitely.** That is the owner's decision in `interface/architecture.md`, and it cuts the old HTTPS bundle in three. Browser login and session to a Cell you are using as a client is modelled, not cancelled, and no task may depend on it. A secure origin for serving a Facade is still planned and belongs with the Facade work, because a Facade is a published read-only projection a stranger looks at and needs a name and a certificate to be reachable at all. The off-LAN camera gap is real and survives the browser-client gate, and is pushed later.

**Reach defaults, restated because the profile work must not reverse them.** Relay-only stays the default and mDNS stays off and time-bounded. Both are built.

**The two-tier roster is not a setting.** `engine/src/directory.rs` filters `cell.front_door` and hard-caps at `MAX_PUBLIC_CELLS = 4` because a `SignedPacket` will not carry a full roster. It is a hard constraint and no configuration can widen it.

**`engine/src/directory.rs` is not the directory Cell.** It is pkarr publishing of the public front-door tier; the queryable index a relay hosts is a different, unbuilt thing. Do not let the shared word hide that.

**Relay-only costing nothing that matters is a conclusion, not a task.** It holds once the relay depended on is your own.

**Repository housekeeping, still true.** The eleven logo files live in `assets/logo/` with `assets/photos/`, and every `include_bytes!` in `lince_website/mod.rs`, `static_assets.rs` and `desktop/src/tauri_shell.rs` was repointed at them — before that, `crates/web` and `crates/desktop` did not compile at all. The four `raw.githubusercontent.com` URLs in `README.md` were fixed with them. The URL strings inside the generated website — `"assets/black_in_white.ico"` in `visual_identity.rs` and `html.rs` — are deliberately unchanged, because those are the exported site's own layout, not repository paths. `anicca/interface/First Steps.linguai` is intentionally agent-maintained and not parsed by Instinct; the six dangling `#part-of @first-steps` assertions were removed from `Lince.lingua`, so the current chapters stand as roots until it is promoted back.

## 3. Organ management, discovery, relay and Facade

Discovery and Relay are ready to implement. This cluster was parked wholesale and that is no longer right: its device- and contact-facing surfaces were the parked part and they have moved to the interface plan, and what remains — T0 and T1 of the profile, multi-hop discovery and gossip, the directory Cell, and Relay Cells — is protocol and infrastructure work whose design is settled below.

Two conditions on starting, neither of which is a reason to wait. The profile editor is part of the profile work rather than a later task: T0 and T1 publish things about a person, the whole risk is publishing more than they meant to, so the editor showing what each tier reveals and to whom must exist before anything publishes — it is listed in the interface plan alongside the rest, and the two land together. And Relay Cells begin with the role; everything else in that section is shaped by it and cannot land first.

### ▢ The Organ Profile, tiers T0 and T1

Cut by size, never by audience: a stranger three hops out must never see more because they are far away.

- [ ] Make T0 carry a structured pair, display name and profile version, in 245 bytes of text. It is currently a bare clipped display name — `wire.rs:955-958` truncates to `UserData::MAX_LENGTH / 4` and sets it. No image ever, and T0 lasts forever.
- [ ] Keep the published organ key off T0. A Cell's NodeId is exposed by mDNS as a matter of how mDNS works, but the organ key is additive and avoidable, and it is the value linking every one of your Cells to each other and to your public profile — broadcast on café wifi, a passive listener keeps a permanent handle. The key arrives after connect, so a nearby row shows no card until then.
- [ ] Build T1, the card, a few KB and the only tier that gossips: name, description, organ key, coarse area if set, a small inline avatar at 128px webp and 4–8KB, pronouns and language as first-class fields, a reachability hint saying direct, relay-only, or that an always-on Cell exists without ever naming the Cells, and what you are offering or looking for, whose payload is OPEN promises. Consent is what separates the organ key from T0, not readability — and the signature needs it.
- [ ] Make the card degrade to its text half over low-bandwidth radio rather than fail.
- [ ] Sign the card with the organ key, for integrity and not identity, and drop a card whose signature fails silently. A badge that can be absent is a badge, and a badge is the verification checkmark returning through the side door.
- [ ] Give the card a version number, a TTL, and a cache eviction lifetime that is separate from the card's, plus a last-updated timestamp so a stale card looks stale. Without the separate lifetime a content-addressed image outlives the card that referenced it and the deleted-photo-returns-forever problem survives the fix aimed at it.
- [ ] Content-address every image and every Facade.
- [ ] Take the coarse area as a self-declared country, region, city or neighbourhood, the Organ's choice, and never derive it from IP or GPS.
- [ ] Keep the Cell roster, the contact list, and any link rendered as anything but plain unverified text out of every tier. The roster leaks device count and online time.
- [ ] Make gossiping your card opt-in per tier, with none implying the next. A travelled card cannot be recalled.
- [ ] Default the coarse area to unset, and to its coarsest granularity when set.
- [ ] Make the seen-set, the per-source budget and the age expiry mandatory rather than tunable. They are what keep the flood bounded, so an operator must not be able to widen them.
- [ ] Make publishing into a directory a separate explicit act from gossiping.
- [ ] Keep the invite door default-closed.

### ▢ Multi-hop discovery, gossip and the directory

Everything built finds a peer you already hold a key for, or one in mDNS or BLE range. Neither answers "there is a Need three hops away I have never heard of."

Gossip cannot reach the world, and the TTL is not the reason why: a flood with no hop limit means every participating Cell eventually stores every profile and every OPEN promise on Earth, which is arithmetic and not policy. The TTL exists first to keep the network from melting and only second to limit exposure, and reading it as a privacy knob invites someone to raise it because they do not mind being seen, which is the one change that breaks everyone else's storage.

- [ ] Propagate OPEN promises past direct contacts, hop by hop, with a TTL and a per-hop visibility check. The payload and the route already exist — `organ_open_promises` serves `GET /organ/open-promises` (`web/src/lib.rs:1535,2011`) and already exports what a subject may publicly see — so this is propagation, not a new message type.
- [ ] Build the gossip cache and the delegated ask-around search, the pull half of the same mechanism: asking a contact to ask onward on your behalf, under the same hop and TTL limits, and holding what comes back. Only the hop-limit reasoning is written down; no mechanism exists.
- [ ] Design world-reach discovery beyond gossip before building anything for it. It is named as a mechanism distinct from gossip and from the directory and has never been designed, and it is not the directory Cell by another name — it is the open question of what reaches past both.
- [ ] Dedup the flood on content hash with a seen-set. TTL bounds depth, not fan-out multiplicity, and in any graph with cycles the same card arrives by many paths; TTL alone is the classic Gnutella flood failure.
- [ ] Forward to a random subset, not to everyone.
- [ ] Enforce a per-source rate budget. One Organ republishing in a loop is indistinguishable from an attack and costs every relay downstream.
- [ ] Expire by age, independently of remaining hops.
- [ ] Depend on nothing a sender says about hop count — it is spoofable, and a relay drops past the limit it chose itself. Keep hop count, `nearness` and `proximity` as three different things and conflate none of them in the UI.
- [ ] Build a directory Cell: a queryable index an Organ publishes into and others search. This is the unbuilt thing that `directory.rs` is not.
- [ ] State the directory's disclosure where someone searches. Its trust story is its own and it is worse than a relay's — a forwarding relay sees what passes through it, but an index sees every query, who is looking for what, when and from where, and that disclosure lands on the searcher.
- [ ] Make several independent directories the mitigation and bless none of them. One blessed directory is a naming authority in all but name.
- [ ] Resolve an area search against the self-declared coarse area and nothing else.

### ▢ Relay Cells

The first item is the new role; the rest are shaped by it and cannot land first.

- [ ] Build the relay role: a Cell willing to carry other Organs' traffic onward. `iroh-relay` only rendezvouses and falls back for two Cells that already know each other's NodeId, so a discovery relay is a different role and new infrastructure, not a mode switch.
- [ ] Keep a relay and a townsquare separate in configuration and in the interface, so an operator never believes moderating a townsquare gives them power over what a relay forwards. There is no middle option — a box that holds plaintext just to help is a full Cell with none of a full Cell's accountability.
- [ ] Make consent to relay explicit per Cell, with a test that a Cell which never opted in forwards nothing.
- [ ] Make relay mode use `relay_capabilities()`, with a test that a published relay Cell is refused capabilities outside that set. The empty set exists (`roster.rs:177`), `cell_may` enforces it, and `engine/tests/enrolment.rs` publishes it in five places — and nothing in the running app does.
- [ ] Give a relayed batch a signed batch envelope, one signature per batch and never per op. Per-op signing puts asymmetric crypto in the typing path, where a burst of keystrokes is a burst of `crdt` ops; this belongs with relay work and never as a tax on ordinary sync.
- [ ] Make relaying a contact's ops per-contact and default it to forwarding nothing, with a test. Forwarding to your other contacts is a disclosure nobody in that chain consented to.
- [ ] Add a per-peer connection cap. None exists: the Nix options are `services.iroh-relay.*` and `services.lince.*`, there is no `services.lince.relay.*`, and no cap of any kind appears under `scripts/deploy/nixos/`.
- [ ] Add byte accounting against a configurable ceiling, so the operator sets one number.
- [ ] Decide the one option namespace for both, alongside the role above.
- [ ] Say in the Discovery panel when a peer is being throttled.
- [ ] Give long-range low-bandwidth radio its own adapter from the start. LoRa is its own transport rather than a variant of iroh or QUIC — its own framing, a tiny payload budget, and almost certainly store-and-forward.

### ⏳ LAST — T2, the Facade

An HTML page, fetched on demand, never gossiped. A person builds a sand describing themselves from their real data and exports it, and `crates/web/static/presentation/board/archive.js` already exports a workspace as one self-contained file.

A different thing shares the name: `anicca/interface/facade.md`'s Live Facade is a published read-only rendering of one Box composition at a public URL, late-v1 product work with browser parity proven, while the T2 Facade here is an exported file fetched by hash. Same word, two mechanisms, and do not let it hide that the way `directory.rs` and `Reach` already tried to.

- [ ] Reconcile T2's no-network wording with the two delivery modes in `anicca/interface/interoperability.md` before implementing dynamic Facades. That plan splits delivery into static — the frozen no-network archive described here — and dynamic public, a stream of signed content-addressed generations pushed to caches, and it already carries the manifest, query-ceiling, withdrawal, safe-renderer and no-tracking work as its own list. The threat model below holds under both modes; the delivery design belongs to that plan.
- [ ] Close the beacon channels with a CSP and an empty sandbox. Scripts-off HTML still beacons through `<img src>`, CSS `url()`, `<link>`, webfonts and form actions, each telling the author who opened their page and when, so "JavaScript disabled" is not what makes this safe.
- [ ] Sanitise on receipt rather than on export, and refuse a Facade that fails sanitisation instead of cleaning it. A hostile author hand-writes the HTML and never runs the exporter, so the receiving Cell must run the strip, inline and neutralise pass over the sender's file as raw untrusted input — and rendering the stripped remainder turns a partial-strip miss into a live bypass.
- [ ] Render a Facade inside a bounded card that visibly belongs to someone else: never fullscreen, never chrome-shaped, never able to present anything reading as a Lince prompt. `archive.js`'s layers are anti-exfiltration, not anti-deception, and sandboxed static HTML can imitate Lince's chrome and phish a password.
- [ ] Fetch only on an explicit click. Pulled because a card scrolled into view, it is a passive beacon in everything but name.
- [ ] Draw links inside a Facade as inert visible URL text that does not navigate, with click-to-confirm showing the full URL as an explicit per-viewer setting.
- [ ] Fetch by hash from any holder, never from the origin Organ, not even as a fallback, and render nothing on a cache miss while saying so. An origin fetch offered on a cache miss would be taken almost every time a Facade is new, which is precisely when the author most wants to know who is looking.
- [ ] Bound Facade storage with a per-Facade size cap shown before the fetch, plus relay-side eviction.
- [ ] Reduce fetch-side leakage by fetching through the relay you already use. Render-side leakage is solved and fetch-side is not; the mitigation is not anonymity but choosing a server who already knows you.

### ⏳ LAST — the public face of an Organ

The public face is an Organ you share a subset with, and its narrowing is the outbound per-field scoping, which is built. It waits on the Facade it serves.

- [ ] Show a published-subset view: what the public Organ actually holds, shown as data rather than promised in a settings screen.
- [ ] Generate the Facade from the public Organ, not the internal one. This is not a deployment preference: a generator running where everything is visible is trusted to omit the right things, while one running on a box that only ever received the published subset cannot leak what it does not have. It is why the public face is a separate Organ rather than a Cell.

### ⏳ LAST — Deployments, as Resenha scenarios

- [ ] `iroh-relay` on the VPS. The module is complete on its axis — `scripts/deploy/nixos/iroh-relay-module.nix` generates the TOML and `vps-module.nix` opens the ports and asserts relay and Lince run as different users — so what it needs is a public IP, a DNS name and TLS.
- [ ] A Cell on the VPS as a roster member: `mode = "server"` in `lince-module.nix`, enrolled like any device, on a different machine from the relay's user and state. This is what makes "edited on the phone all day, walk in the door, laptop converges" work without both being awake.
- [ ] The blind mailbox actually deployed. It is wired end to end in the module and only the deployment is missing; naming is settled, with `mode = "relay"` having become `mode = "front-door"` because one word named three different boxes.
- [ ] "Where this Cell is reachable from" in the Discovery panel. A Nix module with no way to see whether it is working is a config file, not a feature.

## 4. Sync and login and sessions

Three of the four parts of one consent handshake are settled: the read side landed as `offers::pending`, the scheduler was attempted and refused because the two schedulers back off different objects, and the refusal memory is built for all four kinds. The table of how the four differ is history rather than a plan — every one of them records a refusal, and none of them tells the sender. The UI it owes is in `interface/plans/interface.md`, all of it reading `offers::pending`: one pending-offers list with every kind side by side, each row saying who it is from or to and what it is over, accept and refuse on the row routed to the kind's own verb, the honest empty state, and one delivery state per row rather than receipts in one place and checkpoints in another — with a refusal never looking the same as an offer that was never answered, in the three kinds that deliberately do not remember one.

- [ ] Build the "did it arrive?" surface, where receipts and checkpoints answer one user question two ways. Keep the delivery semantics and the domain objects apart.
- [ ] Give the Facade a secure origin — a name and a certificate — as part of the Facade work. A Facade is a published read-only projection a stranger looks at, so it needs one to be reachable at all; this is the Facade's cost, not login's.
- [ ] ⏳ Close the off-LAN camera gap when there is a mobile Lince. `getUserMedia` needs a secure context, so QR scanning fails over plain HTTP to a LAN hostname — and that is your own phone enrolling against your own laptop, a Lince client on both ends, so it survives the browser-client gate. There is no mobile Lince yet, so the scenario has no second device to happen on: the gap is real and cannot be hit. When it comes back, pairing over the wire may be a better answer than a certificate, since the camera was only ever one way to carry a code.
