# Password-locked Record descriptions

A Record description can be a vault. Its description is encrypted with a password while the Record's title, quantity, assertions, grants and other fields remain ordinary Record data. The encrypted description travels through sync and backups as ciphertext, so the same vault Record can be available on another Cell without giving that Cell the plaintext.

The envelope is one line of text and lives in `utils::vault`. It reads `lince-vault.v1 m=19456,t=2,p=1 <salt> <nonce> <ciphertext>`, with the three Argon2id parameters written into the envelope so an old envelope still opens after the defaults change, and the salt, nonce and ciphertext base64. Argon2id derives a 32-byte key from the password and XChaCha20-Poly1305 encrypts the description under a fresh 24-byte nonce. The Record uid is the authenticated data — the string `lince-vault.v1 record <uid>` — so an encrypted description moved to another Record no longer opens. A wrong password, a changed uid and damaged ciphertext all return the single `VaultError::Unopenable`, and never partial text; text that is not an envelope at all returns `NotAVault`, which is a different thing and says so. The derived key and the decrypted bytes are zeroed when they go out of scope.

Every surface that shows a description asks the same recogniser first. `utils::vault::is_locked` answers in Rust and `/board/vault.js` answers in the sands, so a locked description renders as the locked label instead of an envelope: the Record sand shows it in place of the body, the kanban shows it on the card and does not open its in-place editor over it, and the record editor refuses to join. Nothing tries to parse, render or link ciphertext as ordinary text.

Locking, unlocking and password entry are local host calls — `POST /host/vault/lock` and `POST /host/vault/unlock` — and never a Record Action. The password crosses the loopback boundary and is forgotten; only the finished ciphertext goes on to the ordinary Record edit path, `Action::EditRecordText`, so the op log, the Facts and every Organ that syncs this Record see ciphertext and nothing else.

A vault description never joins the shared Loro doc. A character-wise merge over an envelope would produce ciphertext no password opens, and an unlocked body in the doc would sync the plaintext, so the Record sand stops collab for a Record whose body is locked and saves an unlocked vault through the lock call rather than the text Action. The head still saves the ordinary way. `@slug` references are not harvested out of an unlocked description, because that would turn the plaintext into links anybody can read.

Unlocking is local and temporary. Passwords and plaintext never become Records, Actions, Facts, configuration, logs or synced state. The Record sand holds the password only while that Record is in focus: changing focus, going idle or pressing Forget drops it and clears the text on screen.

Each saved edit creates another Record revision. Changing a vault password protects the new description with the new password, and it cannot erase older ciphertext or stop an old password opening a retained old revision. The Record sand says this before it changes a password, and the change is refused until the person confirms it.

Login password hashes, Cell identity keys, public keys and ordinary configuration keep their existing purposes. This vault does not replace their storage or change the encryption already used for transport and sealed messages.

A provider token reaches a cub as an environment entry on the spawned process, never as an argument, because arguments are readable by anything on the machine. `fiote::ProviderCredential` carries the variable name, the secret and where the secret came from; it is set on the `Command` at spawn and zeroed as soon as the cub is running, and its `Debug` prints the variable and the source but not the value. `CubSpec` never holds a secret. What survives the spawn is the label: `CubStatus.credential_source` says `environment` or `vault Record`, so local development does not behave differently without explanation. Environment variables remain a useful Fiote developer path, and `ProviderCredential::from_environment` treats an empty variable as no credential at all.

Karma does not read or reason about secrets. `InputSource::SecretMetadata` was speculative and never resolved a value, so it is gone from the AST, the DSL, the proof, the evaluator and run preparation, and the tests that used it as a convenient external boundary now use honest Signal and Record inputs. The wire vocabulary shrank, so the golden hashes in `karma_k1`, `karma_evaluate` and `karma_replay` were regenerated.

Two honest limits. A Record that is mirrored to a file by file sync is a poor place for a vault: its ciphertext is written to the file like any other body, and an edit on disk replaces it. And locking is a whole-body replacement, so two Cells that lock the same Record while apart will keep one envelope and lose the other, the way any other divergent whole-field write does.

What is verified: round trips, a fresh salt and nonce per lock, wrong passwords, tampered ciphertext, ciphertext moved between Record uids, ordinary text told apart from a bad password, the locked recogniser in both languages, the locked rendering in three sands, and a Record whose locked description reaches the store, the Facts and the sync ops as ciphertext with an older revision still opening under its old password.
