# Backend Part A — Dogfeeding

Dogfeeding is the first usable part of Lince v1.0.0. Its acceptance case is a private software house managing knowledge, projects, cards, tasks and discussion, with control over who can see and change the work. The deliverable is general Lince capabilities used by that company, not a company application built alongside Lince. Completion means the company can use them through the new Interface Sands, not that every backend API or every official Castle has been implemented.

The company's shared context is an Organ. A Linux server, on a local machine or VPS, is a Cell serving that Organ, not a new definition of Organ and not the owner of employees' personal Cells. For this deployment, it holds the authoritative shared data. An employee enters as an identified Person; administering this Organ does not confer access to that person's other Organs. The same model and policy apply on a local network and from home.

The client is the new native Lince Interface and its Sands, running on employees' computers and entering the shared Organ in live mode. It does not require the `lince-desktop` wrapper, its old Sands, an embedded browser, or a local replica of the shared database. An employee may already have a personal Cell for identity and transport without becoming a company replica or a privileged Organ roster member. A web-browser client is a separate delivery decision, outside Part A.

This plan owns the backend foundations and their Dogfeeding acceptance. [The Interface Part A checklist](interface/plans/part-a.md) owns their controls in the new native Sands. A backend checkbox cannot close a user workflow without those controls.

## What is included

Projects, teams, tasks and knowledge remain Records, described by Concepts and Assertions and read through Protein. A project can be marked `#project`, a task `#task`, and their relationship can use `#part-of`; these are examples chosen by the administrator, not required names, new Record kinds or a second project/team store. Records need not belong to a project or have exactly one parent. Existing work metadata supplies assignment, dates, estimates and work logs. Status and priority have chosen meanings rather than being guessed from a number. Kanban, Todo and Table are views of those same Records.

The essential surfaces are Organ connection and login, Record and Assertion editing, configured Protein reads in Kanban/Table/Todo, threads/messages, and administration of People, Roles and access. Project navigation and My Work are uses of those surfaces, not mandatory special screens. The administrator can create the vocabulary, policies and saved views by hand from an empty Organ. A company starter, setup wizard, templates and automatic board wiring are not Part A requirements. Shared native controls, configuration, keyboard access, stable placement and the editor remain foundations; full Ontology and Relations explorers are not required for basic authoring.

Live company work means authorized reads and writes against the company's server, with updates reaching other permitted viewers. It does not mean a shared Box document, shared camera, synchronized Sand positions, offline company replicas or host failover. Those remain separate later work. During a connection loss, the Interface reports that state and never claims a change is saved on the server without its receipt.

Karma and Transfers, including their Castles, are outside this milestone. Communication is task/project threads and messages, not calls, media rooms or a separate Communication Castle. Fiote, a code-execution harness, repository hosting, automatic PR creation, public discovery, Facades, Calendar/Clock, moving Areas, custom shaders and CEF are also outside Dogfeeding. Their source and remaining plans stay; none is a prerequisite or an automatically enabled company feature.

## Starting point

The following source findings describe the starting point of the backend build. The Git history records what has since been implemented and verified. A verified foundation does not complete a user workflow by itself.

The owner-authored [Lince Record](Lince.lingua) supplies the model: Records, Assertions, work metadata, People, Cells and separate Organs. Its Organ chapter explicitly describes an Organ as a shared context rather than a server owning its members. A central company deployment fits that model without changing the rest of Lince into a central service.

`crates/lince/src/main.rs` already accepts `--server`, `--data-dir` and listen-address options. Server mode selects `HttpServeMode::ApiOnly` and forces authentication. `scripts/deploy/nixos/lince-module.nix` already describes a headless server service. These are reusable source paths, not proof that a private Internet-reachable company deployment has passed acceptance.

`crates/engine/src/wire.rs` declares `ALPN_LIVE = lince/live/2`; `crates/transport/src/live.rs` serves a Person-bound session over that connection. The Web live proxy and `crates/transport/tests/live_workflow.rs` demonstrate existing integration points. The native `domain.rs` is currently a local-URL client, while `crates/interface/src/main.rs` still starts the laboratory. A product-ready native remote entry must therefore be proved, not inferred from the binary's name or from a loopback test.

`Action::CreateUser`, `CreateRole`, `AssignRole`, `GrantPermission`, `RevokePermission`, `SetPersonStanding` and `SetPersonReadFilter` exist. Roles currently carry action permissions, and a credential row has one Role. `person_credential.read_filter` stores a separate Protein predicate per login; NULL means no additional narrowing, not deny-all. Protein supports Concept and relation predicates, including `Under`; its selected output fields are not property-write permissions. Role-associated Record selectors, property-write permissions and proposed-state checks are new B05/B07 work, not a rename of that per-person read filter.

Permission coverage is not complete enough to certify the company promise. `protein::execute_for_with_context` intersects visibility with the person's filter for several sources, but the Assertion source calls an implementation without that visible set. `engine::may_read_record` in `collab.rs` checks visibility without the person's filter. `Session::CollabUpdate` currently uses the read check, and `on_fact` can emit a joined document snapshot without repeating it. `read_filter::record_targets_of` covers only a subset of Action targets. These are concrete places to unify and negatively test the policy; a filtered Kanban is not evidence that every route is safe.

The existing visibility query also includes Records on whose Facts the Person appears as author. Removing a Role grant or changing a policy-relevant Assertion must therefore be tested against previously authored Records, not only untouched tasks. A former author must not retain access accidentally through another visibility rule.

These starting findings came from source reading, before implementation tests. The execution graph carries revision-bound build and runtime evidence; it does not imply a production deployment or independent security certification. Concurrent edits, including locked descriptions, must still be reconciled at each accepted implementation revision.

## The access model

The decision is to give Roles operation permissions over Protein-selected Records, including permission to write particular Record properties. Protein describes the Records; the Role grants authority; the server checks the operation; Sands let people use and inspect it. A Person receives a Role, not a separately maintained copy of every policy. B05–B08 deliver this contract; the existing coarse permissions and per-person read filter do not already provide it.

Read, create, update and delete are separate permissions. Create and update grants name their Record sets and allowed properties, such as body, quantity or assignees. Assertion permissions can distinguish the predicate and target being added, removed or changed; allowing ordinary status changes need not allow every Assertion. Permission to read does not allow editing, and permission to edit the body does not allow assigning oneself, changing authority or replacing arbitrary fields. A grant must cover the operation's targets and all changed properties; a property permission for one set of Records cannot be borrowed for another set. Restore is checked as a current operation, not an exemption for past permission.

Creation is checked against the complete proposed Record and its Assertions. An update is checked against the current Record, the complete proposed result and the properties actually changed; deletion is checked against the current Record. Dogfeeding does not introduce blind writes to hidden Records. If a user's policy excludes Records bearing the administrator's chosen `#admin` Concept, the user cannot create one, add that Concept to an ordinary Record, or remove it from a hidden Record to obtain access. Copy, import, restore, card moves, bulk Actions and collaborative text obey the same rule when those paths are enabled. Reclassification must be covered by the Role's Record and Assertion-write grants on both sides; a general edit button is not that authority.

The `#admin` Concept is not a reserved security switch and is not the same thing as a Role named admin. Policies refer to the actual Concept and relation identities, not whatever currently shares a displayed slug. Role assignment, policy definitions and any Assertion, membership or relationship used to determine access are protected changes. A person cannot obtain equivalent authority by editing a parent, team membership, alias or policy dependency instead of the protected Record. A cross-link grants nothing by itself; traversing a relation grants access only when the policy explicitly says so. Projects and teams have no built-in ownership or inherited access rule.

A displayed Protein is a view, not a grant. A card can leave an open board when its status or assignee changes without becoming an unauthorized write, provided the Role permits the change and resulting Record. A saved view runs with its viewer's authority, never its author's. Query output fields are presentation choices, not property-write permissions. Part A adds no separate field-read secrecy system: an allowed Record's content is readable subject to existing locked-description protections, while linked Records and included metadata still require their own read checks. Read authority does not unlock encrypted content. Keep separately protected information in separately protected Records.

The policy uses Protein's typed predicates, with bounded, deterministic server evaluation and explicit refusal of unsupported predicates or missing authority. Selection is against the relevant current or proposed state, not a stale query page or a match reported by the client. Any Actor/Organ binding comes from the authenticated session through a typed binding, not client-supplied identity or string substitution. This reuses Protein without adding another policy language, arbitrary scripts, Karma Rules or Transfer grants. Existing Organ/Record restrictions remain ceilings; if the per-person filter is retained, it can only narrow further. A missing or invalid Role policy grants nothing. The current single-Role assignment is sufficient; multiple-Role inheritance is not a Part A requirement.

A permitted change is committed together with its checks at the relevant Record, Role and policy-dependency revisions. An access change racing an edit cannot pass against one state and commit against another. Multi-Record Actions validate their actual write set; task creation is never visible between creation and required Assertions. Server-derived changes are explicit parts of the typed Action, not a way for a caller to smuggle arbitrary properties. Unknown write paths are refused or unavailable until covered. The same decisions supply native allowed-operation/property information and useful refusals without revealing hidden Records.

Live access does not make an employee computer trusted with Organ replication keys. A private deployment refuses unapproved discovery, public projection, contact sync, export and privileged host operations as well as unauthenticated reads. The Organ administrator and server operator are trusted with server-held plaintext; this plan does not promise end-to-end secrecy from them. Revocation stops future authorized access and clears compliant client state, but cannot recall screenshots or other copies a person already made. Manual setup removes convenience work, not authentication, a safe initial administrator, auditability or recovery.

## Establish the foundation before dependent UI work

- [ ] **B00 — Fix the launch contract.** Record the accepted source revision and included concurrent edits, select the employee operating systems for the new native Interface, and map every Dogfeeding operation to its actual read, Action, authentication and persistence path. Name the Role policy, property identities, supported Protein predicates and atomic check/commit contract before dependent nodes diverge. Re-cut missing paths into owned graph nodes with runnable proofs; retain excluded native and CEF work outside this milestone. Do not dispatch the old whole-catalog graph unchanged.
- [ ] **B01 — Qualify the private Linux server.** Reuse `--server` and the existing service/package path, proving headless startup without a display or CEF, forced login, deliberate data-directory and port configuration, restricted service account, safe initial-admin setup, restart behavior and a useful failure when configuration is invalid. Default company discovery, public publishing, replication and unused host capabilities to unavailable unless explicitly authorized; do not advertise a private deployment merely because its board HTML is hidden.
- [ ] **B02 — Complete the native live connection.** Reuse the existing live protocol behind a general Organ connection/profile adapter and the shared production Interface host, without requiring `lince-desktop`, legacy Web rendering or Organ-database replication. Bind every read, write, subscription and receipt to the selected Organ and authenticated Person. Show the verified Organ identity, account and connection state; changing Organ must not submit the previous Organ's pending work.
- [ ] **B03 — Prove access from home.** Document and test one supported encrypted remote route to the company server, including server identity verification, invitation/address setup, firewall and NAT or relay requirements, and reconnect after moving between networks. Prefer the existing live transport where it meets the requirement; do not expose plaintext password-bearing HTTP as the remote solution or require public company discovery. A same-machine loopback test does not prove this journey. Record infrastructure choices and obtain the operator's agreement before deployment.
- [ ] **B04 — Finish Person account lifecycle.** Connect existing People, credentials and Roles to the new native administration/login controls: create a Person, assign their Role, change credentials through a safe recovery path, disable/reactivate and end access from a lost device. Team membership is expressed through ordinary Records and Assertions, not a second account system or automatic credential grant. Distinguish a Person login, a granted Organ login and privileged Cell enrollment. Test each admitted authentication path, including a granted Person with no ordinary credential row; a missing Role/policy must not become unrestricted access. A worker needs neither an admin credential nor an Organ signing key to edit cards.
- [ ] **B05 — Give Roles Protein-scoped and property-scoped permissions.** Add one authoritative Role policy representation over existing operation permissions, with separate readable and writable Record selection and explicit create/update/delete/restore permissions; create/update grants name canonical properties and permitted Assertion changes. Keep the current single-Role assignment, default-deny onboarding and existing authority ceilings; a retained per-person filter only narrows them. Validate the supported Protein predicate subset, limits, trusted context bindings and current/proposed-state evaluation; never reuse a permissive unsupported-predicate fallback or presentation projection as authorization. Supply typed policy administration and an access preview for a selected Person, Record and proposed change without impersonation or revealing withheld content. Include discussion, vocabulary and allowed Person references explicitly where needed, with no mandatory owning project, per-person project list or hardcoded Concept name.
- [ ] **B06 — Close every read path over that policy.** Apply the same effective access check before serializing direct Record lookup, Protein sources/includes, assertions and Concepts, search/autocomplete, saved views, aggregates/counts, facts/history, threads/messages, collaborative snapshots and enabled file/export paths. Restrict or reject unsupported sources rather than leaking them through an unused panel's API. Check nested targets and error text as well as top-level rows; withheld is not empty, and knowledge of a uid is not access.
- [ ] **B07 — Check every write and its proposed result.** Require a verified active Person and matching Role grant for each admitted typed Action and collaborative text delta. Compute actual changed properties, affected Records and policy dependencies on the server, including Assertions, work metadata, quantities, drafts and server-derived changes. Check create against the complete candidate, update against current and proposed state, delete against current state and restore against current authority and restored state. Commit checks and writes atomically or reject revision races; multi-target operations cannot expose a partial protected reclassification. Enforce property limits on whole-Record and CRDT writes, protect policy/Role/membership dependencies and reject unauthorized references. Prove the forbidden `#admin` creation/addition/removal cases across every enabled entry point. Unknown paths and internal no-actor calls cannot become remote bypasses; reading never grants text-write authority.
- [ ] **B08 — Apply access changes to open sessions.** Invalidate or refresh affected subscriptions, lookup caches, collaborative membership and queued operations when a Person, Role, policy, policy-relevant Assertion/relation/membership or login grant changes. Recheck read and property-write authority before further snapshots or writes, including already-connected clients and previously authored Records. Prove storage/authentication errors fail closed, a revoked client cannot resume its old grant, and pending edits are not silently delivered after authority was removed. No stale policy preview or cached allowed-field list is authority.

## Make knowledge, tasks and discussion work together

- [ ] **B09 — Complete generic Record and work authoring.** Reuse Records, Concepts, Assertions and existing work metadata to create knowledge, projects, teams and tasks, assign people, choose status and priority, set dates and estimates, record work, edit title/body and archive work. Let the administrator define the vocabulary and configure fields and views manually through the new Sands from an empty Organ; no company starter, templates, wizard or Instinct corpus import is required. Supply missing typed authoring operations with native controls, including atomic creation with required Assertions, rather than a second task/team table or scripts hidden in a Sand. Preserve the difference between quantity zero, completion, archive and deletion. No Record must have a project merely to exist.
- [ ] **B10 — Qualify reusable work views.** Serve bounded, permission-filtered Protein reads in Table/Kanban/Todo and search, with stable row identities, saved configuration and useful empty/refused states. Let manually configured views provide project lists, team work, knowledge lists and My Work across any permitted Records. A saved view is a definition, not its author's authority; evaluate it for the current Person. Distinguish permission to edit shared configuration from changing one's own display filter. Prove that view configuration never grants access and that a permitted edit can move a Record out of the current view without being rejected merely for that reason.
- [ ] **B11 — Preserve concurrent work.** Connect the native shared text editor to the authorized collaborative contract, with delta acknowledgement, reconnect/deduplication, bounded presence and clean teardown. Scalar edits carry a revision or equivalent explicit conflict check so a late form does not overwrite a colleague's newer field. Preserve refused edits for the correct Person and show a recoverable conflict. Locked descriptions remain opaque and never enter a shared plaintext text session; inspect accepted vault behavior rather than weakening it for convenience.
- [ ] **B12 — Make receipts reliable across retries.** Use stable operation identity scoped to the authenticated company/Person and the existing signed Action-intent path where applicable. Prove duplicate delivery and a lost acknowledgement do not create a second task, message or work-log entry; an id reused with changed content is refused. Record server acceptance separately from local pending state, recover the outcome after reconnect, and never claim exactly-once user effects merely because the socket delivered one frame.
- [ ] **B13 — Finish Record discussion.** Reuse thread/message Records and `CreateMessage`, with native access from a Record, correct authorship, ordering, replies where supported and author-private drafts. The Role's Protein policy governs the discussion and every included message; a thread is not implicitly public because its parent is visible. Make discussion scope expressible without requiring project membership, a call-room or another account system. Distinguish a saved draft from a posted message and do not clear a newer draft when an older send is acknowledged. Cross-Organ group membership and Fiote turn controls are not required.
- [ ] **B14 — Make pending work and reconnect understandable.** Define local company-data retention explicitly. The proposed live-only default keeps displayed data and unsent outage edits in memory, stores acknowledged author-private drafts on the company server, and stores only nonsensitive connection/layout preferences locally. An outage is not permission to create an offline company replica. Reauthentication refreshes authority before replay; logout, access loss and identity changes clear visible private state and transient secrets. Warn before losing unsent work; no crash-recovery promise for an unsent memory-only draft. Any durable local company cache requires an explicit policy and its own protection/clearance proof.
- [ ] **B15 — Make activity and Record links useful.** Expose authorized history answering who changed a Record or its access policy, what changed and when, including Role assignments and policy-relevant membership edits. Reuse Facts and available change records; add missing attribution through the supported operation rather than inventing a second task history, and do not imply every text revision is already an audited semantic edit. Provide stable Record links opening the correct Organ and requesting login when needed. Scope previews and activity as strictly as their subjects, protect administrative history and never put credentials in links or logs.
- [ ] **B16 — Recover an accidental deletion.** Deliver the existing newer-write undelete semantics through a supported restore Action and a native Trash/Restore view, preserving original identity and referenced discussion as the domain permits. Validate current Role authority, restored properties and the complete restored access state; recovery must not resurrect an old grant or overwrite newer content silently. Test intervening edits and access changes. This is the Dogfeeding home of the existing Ontology Trash debt, not a second lifecycle layer.

## Make the company safe to depend on

- [ ] **B17 — Prove backup and restore.** Define an operator-controlled backup of the database, required keys, configuration and any enabled server-held assets using a consistent snapshot rather than copying a live database blindly. Document backup access, encryption/protection, retention, expected recovery loss and recovery time. Restore into an isolated replacement server and prove identities, permissions, tasks and discussion still work; revoke or invalidate old sessions as required. A sync peer or the Interface's layout backup is not this backup.
- [ ] **B18 — Give the operator a usable health and recovery path.** Expose protected health information for service availability, last successful backup, storage pressure, active/live-session load and read-model checks without leaking task content into logs or public diagnostics. Bound requests, login attempts, subscriptions, documents and outgoing queues; disconnect slow or abusive clients with an intelligible reason. Prove clean restart, abrupt failure and insufficient-disk behavior without false saved receipts. Keep essential server recovery available if the graphical Interface cannot connect.
- [ ] **B19 — Prove the general access boundary in Dogfeeding.** Build a reproducible isolated fixture from an empty Organ through supported Actions, with administrator, worker, read-only and disabled Roles/People and differently scoped Records. Use real authenticated sessions, owner-chosen Concepts and a knowledge/team example without a required project; repeat key cases with different Concept names to catch hardcoding. Test allowed body edits alongside forbidden property writes at creation and update; creation/addition/removal of protected `#admin`; forged Assertion, Role, team, parent and policy changes; read-only and field-limited CRDT edits; hidden uids/includes/messages; previously authorized authors; admin-authored views; permitted edits leaving a display filter; policy changes racing commits; copy/import/restore if enabled; duplicate sends, disconnect and restart. Inspect the wire and run the corresponding new native controls, not merely filtered screenshots.
- [ ] **B20 — Measure the intended company workload.** Agree a first supported envelope of projects, tasks, document sizes and simultaneous users before acceptance, then measure bounded reads, updates, reconnect and server resource use at that envelope. Keep existing native input/frame/accessibility thresholds for the selected workflows; add a recorded remote latency profile rather than treating network round-trip time as local rendering latency. Pause other project work while measuring and record actual machines, source, fixtures and raw evidence. No invented company-size or operating-system support claim is a pass.
- [ ] **B21 — Run an owner-reviewed pilot from manual setup.** Have the administrator create the vocabulary, Roles, Protein access/property policies, work views and a Person from an empty Organ through the supported controls, without a company wizard or raw database edits. Let that Person connect from a second network, create knowledge and tasks, assign and move permitted work, discuss it, reconnect, and observe read/property restrictions and revocation. Recover a deleted Record and restore a backup into an isolated instance. Record failures and missing UI honestly. Production deployment and import of real company data need separate explicit operator approval; a successful fixture is not that authority.

## Useful additions after the core works

These are recommendations for review, not extra Dogfeeding gates. They should not delay identity, access, task editing or recovery.

- [ ] **P01 — Consider a small in-app attention list.** Show assigned work and unread task replies with per-person read markers and direct links. Reuse authorized task/thread reads; no email service, push infrastructure, Karma rule or new universal notification engine is implied. Decide whether this earns a place in the pilot from actual use rather than adding every notification channel now.
- [ ] **P02 — Consider screenshots and small task attachments.** Use authenticated company-server storage and fetch for the company-only live workflow, with size/type limits, explicit upload success and the task's access policy. Ordinary links can suffice for the first pilot; a host-local image path must not pretend to be a file colleagues can retrieve. Cross-Organ blob federation and embedded PDF/EPUB rendering remain separate Files/CEF work.

## Ordering

B00 cuts executable nodes; these checkboxes are requirements, not invented passing commands. The native CEF-free host/bootstrap and private server packaging can proceed alongside Role policy work once their files are separately owned. B05 fixes policy and property identities before B06–B08 enforce and invalidate them; the graph can split those requirements into owned nodes without inventing competing policy systems. B02–B08 and A03.3 meet at the same native identity/access contract. Generic authoring, configured views, editing and discussion then consume it; backup and operator work can proceed independently where their real dependencies permit. B19–B21 close the combined backend and Interface milestone. A company preset is not a predecessor to any of these.

Work sequentially on the current branch. Run the focused Cargo test that proves each change, and run broader checks only when a shared contract or release boundary requires them. The server target needs its own production proof; a library test does not prove it. Use one compiler at a time and pause unrelated work during measurements.

Existing checks such as `crates/engine/tests/auth_actions.rs`, `read_filter.rs`, `crates/transport/tests/session.rs` and `live_workflow.rs` are starting evidence to inspect and extend, not substitutes for the company fixture. At node cutting, name exact files, test targets and commands that fail on the specified negative cases. No production credentials or company database enters those fixtures.

The sweep preserves 22 required backend/acceptance tasks, B00–B21, and two optional proposals, P01–P02. Each requirement has one task home here; Interface tasks own controls, not a duplicate backend policy. The clarified scope replaces a per-person project-access profile, mandatory owning project and company starter with general Role/Protein/property permissions and manual setup. The Organ model is unchanged. New native Interface Sands are the selected client, not the legacy desktop Sands; supported employee operating systems remain a launch choice.
