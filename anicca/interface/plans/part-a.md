# Interface v1 Part A — Dogfeeding

Part A is Dogfeeding: general Lince capabilities exercised in a private company Organ, where people manage knowledge, teams, projects, cards and tasks through the new native Interface Sands. They connect live to an authenticated Linux server on a local machine or VPS, including from home. [Backend Part A](../../backend-part-A.md) owns the foundations, Role/Protein/property policy and combined acceptance. This is neither a separate company application, the historical runtime Plan A nor completion of all C4 roots or all v1. Later Box, Calendar/Clock and native catalog work retain their places in the [master plan](interface.md#v1-master-waterfall).

Dogfeeding ends with Organ connection/login, generic Record/Assertion editing, configured Protein reads in Kanban/Table/Todo, Record threads/messages and People/Role/access administration usable through shared new native Sands. Project navigation, team work and My Work can be manually configured uses of these pieces; no company starter, wizard, automatic board wiring or mandatory owning project is required. Basic authoring works from an empty Organ without full Ontology or Relations explorers. The [remaining native migrations](native-follow-through.md) include Karma, Transfer and the separate Communication Castle; none is required now. The five browser-backed roots and Installed HTML remain unavailable: each needs a way to run without embedding a browser in Lince before it returns, as [the build rule](../build.md#no-embedded-browser) sets out. A working constructor, legacy desktop Sand or backend test alone does not complete a workflow.

This checklist owns Dogfeeding's Interface work; the backend checklist owns its domain and operational work. Existing shared editor, theme, accessibility and proof requirements remain, applied to this selected product rather than an arbitrary root count. Removed migration tasks retain their own home in the native follow-through.

## Bevy-native implementation

The owner selected Bevy on 2026-09-07. Bevy owns the application, window,
input, schedules, UI, text, assets and rendering. New interface code may use
Bevy directly and existing interface code may be rewritten. Do not build a
renderer-neutral widget tree, generic engine adapter or paired HTML output
for new work. Reuse or translate existing backend/data boundaries, retaining
the product behavior and authority they enforce.

First-party Bevy widgets/scenes/observers are the baseline. Lince plugins add
Sand metadata, editable composition, scoped effects, Protein/Action bindings,
styling, view reuse and idle scheduling. Matching AccessKit types and needed
platform-service crates are allowed; custom plugins, internal/external crates
or pure WGPU passes solve named needs within Bevy's lifecycle. Specialized
document, terminal and video engines are end-of-v1 work. No general physics
solver is required by Dogfeeding. Build the foundation with 3D-capable Bevy
transforms/scenes and a planar, orthographic presentation. Avian 3D is selected
for later motion, not activated for ordinary company work. Flair is preferred
for CSS authoring over Bevy UI, subject to integration acceptance. Current
extensions are registered components/effects and trusted Rust plugins;
untrusted executable code and its sandbox are deferred.

The owner's current machine is the [minimum target](../build.md#minimum-machine-and-resource-baseline).
Use its real native-resolution graphics path for acceptance. Later 3D Sands
keep a pinned authored facing by default and offer a Face viewer toggle;
these spatial controls do not become a new Dogfeeding prerequisite.

The source checkpoint below is historical implementation context, not a
constraint to keep the prototype framework. Verify actual source before
reusing it, and do not call old reports Bevy-native evidence.

## Decisions the builders must preserve

Every ordinary label, field, button, menu, row, card, toolbar, error and inspector is a reusable Sand. A specialized document, graph, terminal or game renderer can remain a bounded leaf inside a compound. A Castle is a packaged composition, not another application class. Native Rust is the Part A Interface client path. HTML-backed projections retain their declared package and authority boundaries on paper only; there is no runtime in Lince to execute them, and there will not be one until installed HTML has a browserless execution story. No new browser-client product, TypeScript, Datastar, GPUI adoption or second desktop runtime enters Part A.

The larger Box design is a constraint on these foundations, not permission to implement later work early. Definition identity, child identity, result identity and an individual appearance are different things. One field may feed several Sands. A Record uid can locate multiple appearances and cannot silently choose to edit all of them. Later release changes movement attachment without changing ownership, data lifetime, event scope or permissions. Do not hardcode one property to one widget, use renderer handles as durable identity, or make editor locking imply permanent movement attachment.

Protein reads do not grant write authority. Backend Part A's Role policy selects readable/writable Records and permitted property changes; the selected view and its output fields are not that policy. A body edit, assignee change, Assertion edit, card move and collaborative delta use the same backend checks over the current and proposed Record. A forbidden addition of `#admin` cannot be hidden inside an otherwise permitted edit. Sands consume effective operation/property permissions and preserve readable refusals, but the server remains the authority. A permitted change can remove a card from the displayed view.

A changed presentation does not change Record data. Live refresh must not erase a dirty edit or turn withheld data into an empty value. An Action is acknowledged before the Interface claims success; retries must not multiply its effect. There is one shared Record-body editor, including when a body is shown in Conversation or Kanban. Manual authoring reuses Record, Assertion and Protein controls instead of introducing a company-only vocabulary, project/team store or administrative screen with independent policy logic.

Part A keeps workspace placement stable and preserves existing motion code as an explicit laboratory regression workload. It does not add shared Box layout/camera sessions, general graphs, Calendar/Clock, simulation, Karma, Transfers or a Fiote harness. Collaborative task data and text are required now; later live Box collaboration is a different protocol and is not a prerequisite.

The [MorphoHDL example](https://github.com/paradigms-of-intelligence/morpho) is useful later evidence for describing a structure and watching it grow. It is a circuit language and graph-rewrite demo, not a replacement for Lince's Record model, Sand contract or scheduler. Its exploration stays in the [Sand backlog](sands.md#later-data-authoring-exploration).

## Related feature plans do not become hidden prerequisites

Karma and Transfers, including their old and new authoring paths and their Castles, are outside Dogfeeding. Their [native follow-through](native-follow-through.md) and domain plans retain all remaining work. Do not implement a dispatcher, migrate Rule/Frequency controls or use automation to supply ordinary task editing. Company role permissions do not expose these capabilities by default.

Threads/messages provide company discussion without multi-Organ Rooms or calls. [Files](../../Files.md), [Rooms](../../Rooms.md), [Code](../../Code.md) and [File Sync](../../FileSync.md) remain separate work. Backend Part A records small attachments and an attention list as optional pilot proposals, not automatic gates. A host-local image path is not a remotely delivered company attachment.

[Secrets](../../Secrets.md) now specifies password-locked Record descriptions; this is distinct from ordinary plaintext Record/configuration storage. Concurrent vault utility, Fiote credential and Web reader changes exist in the owner's checkout but this plan does not certify them. If included in the accepted baseline, native Record, editor, Conversation and collection consumers preserve their locked state and supported local lock/unlock/edit path without logging plaintext or sending it through shared text reconciliation. An encrypted envelope is opaque, not Markdown or a character-merge document. Secrets owns its cryptographic contract and Fiote its credential selection and harness; the interface must not reinstate older raw-key storage advice or bypass them. The AI shell and Fiote credential-selection surface are outside Dogfeeding and retain their later tasks; their absence is not a reason to weaken the shared editor's vault handling.

## How the work is divided

Shared native input/definition seams and Backend Part A's Role/Protein/property contracts are prepared before their consumers. Generic authoring, configured reads, edits and threads then proceed through separately owned modules; private-server operations and backup work can run independently where their real dependencies allow. Native quality gates and the manually configured company pilot close Dogfeeding together. Full catalog migration and company-startup conveniences are not hidden predecessors. This refinement preserves 42 Interface tasks; implementation details of the policy remain owned once in Backend B05–B08.

The graph starts conservatively with two builders and one verification agent alongside the planner, matching the four agent slots exposed in this session. The verification agent performs the integrator and inspector roles in separate, serial phases; there is still exactly one shared-file writer and one exclusive-resource owner. A later run with more agent slots may separate those roles and admit more builders, but the measured compiling-tree limit and the zero-compiler measurement window still apply.

Before builders launch, B00 re-cuts the stale graph around the Dogfeeding requirements. Implementation then starts at the qualified native/server and identity/access bootstrap, not at Calendar, topology, custom shaders or a new architecture survey. When a node reveals work outside its files, it reports the exact dependency to the planner. The planner changes the graph; the builder does not improvise a second contract.
