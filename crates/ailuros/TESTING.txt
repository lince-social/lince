Ailuros firmware organization and validation

Rust iroh qualification

The editable export includes iroh's Rust frontend under iroh/ and shares the C
components in components/ and bounded framing in protocol/. The standalone
repository candidate remains under firmware/iroh/. Export adjusts shared-source
and protocol dependency paths; it does not
copy separate implementations of provisioning, identity, networking or capture.

Use nix develop .#ailuros-rust --command cargo xtask ailuros
prepare-iroh-toolchain <tooling-folder> to install/check ESP Rust 1.93.0.0 and
prepare libclang's scoped Nix runtime paths. The ordinary desktop compiler is
unchanged. ESP Rust 1.97 has a demonstrated optimized-codegen failure with this
dependency set; cargo check alone did not catch it.

Export a fresh GOOUUU project with cargo xtask ailuros export <folder>
goouuu-esp32s3-cam-v1.5. Then run nix develop .#ailuros-rust --command cargo xtask
ailuros compile-iroh-check <folder>. This command links the real target, generates
images and records an iroh-qualification artifact with protected NVS bounds.
The qualification frontend is restricted to the verified board profile and does
not replace the production camera workflow. Native camera setup rejects test
and qualification artifacts. Use the explicit guarded flash command only after
reviewing the artifact, selected device and verified rollback images.

The ignored iroh_sdk integration test runs a complete fresh export/link/image
verification without USB access:
nix develop .#ailuros-rust --command cargo test -p lince-ailuros --test iroh_sdk -- --ignored --nocapture
The SDK generates its actual configuration under the esp-idf-sys Cargo output;
ESP_IDF_SDKCONFIG names an optional input, not that generated output. SDK,
partition, toolchain and dependency changes choose a separate target cache.
Workflow code changes reuse that cache. Optional versioned sdkconfig.input files
under iroh/ can override defaults; their contents also select the cache.

The PSRAM candidate uses targets/xtensa-esp32s3-espidf.json explicitly. It keeps
the standard target stem because ESP-IDF's metadata builder rejects other names,
while disabling S32C1I/forced-atomics in the JSON definition. LLVM then delegates
Rust atomic operations to the SDK's existing PSRAM-aware software atomics.
The guarded builder verifies the target settings and the SDK workaround flag.
Do not substitute the bare built-in target name for the JSON target path.
A small optimized assembly probe confirmed the SDK libcall with warnings denied;
the firmware also exercises 40000 PSRAM atomic operations across two threads.
The full image still requires hardware qualification.

The current diagnostic also verifies public RFC6979 P-256/P-384 signatures with
SHA-256/SHA-384, rejects tampered messages, invalid points, truncated signatures
and trailing signature data, and enforces a two-second valid-verification limit.
On ESP it calls the SDK's Mbed TLS through lince_core/verification.c. Host tests
exercise the same algorithm selection and vectors using the RustCrypto backend;
they do not prove the device binding. Rustls retains its normal certificate
chain, trust, name and time checks. Both curve families have verified host TLS
tests. Device qualification must run the SDK-backed checks before iroh startup.

Speed optimization uses scalar code generation: loop/SLP vectorization are
disabled because ESP LLVM 20 cannot select the boolean vectors generated by
the http/rustls crates at optimization level 3. Compiler configuration changes
invalidate the artifact. Ordinary standalone Cargo target/.embuild caches are
excluded from the source digest; actual workflow source remains hashed.

After explicit qualification installation, the host example examples/device_check.rs
accepts the ESP's public EndpointId and direct or relay. Run it through the host
Nix environment with the host target and stable toolchain. It verifies identity,
path selection and three bounded exchanges. It does not authorize camera capture.

Shared iroh framing

crates/ailuros/protocol is a small independent package for both Engine and the
ESP frontend. Run cargo test -p lince-ailuros-protocol through the host Nix shell.
It covers fixed big-endian headers, bytewise partial input, multiple frames,
pre-auth data refusal, size limits before body allocation, non-mutating encoder
errors, cancellation during partial reads and truncated EOF. Use Tokio Util's
FramedRead with HEADER_BYTES initial capacity; its buffers survive cancellation.
Apply auth/read/write deadlines in adapters. The codec does not authorize peers
or validate JSON, JPEGs, Signal grants, epochs or sequences; the shared session
and workflow own those checks.

Exports include the protocol sources, manifest and license notices. The ESP
frontend's Cargo.lock controls its production dependency graph. A standalone
protocol test's Cargo.lock and target/ are disposable caches excluded from the
firmware source digest. Protocol source changes invalidate artifacts but reuse
SDK caches; protocol dependency-manifest changes choose a fresh SDK cache.

Repository ownership

boards/ contains public, versioned hardware profiles. firmware/esp-idf/ contains
shared provisioning, identity, networking and lifecycle code in lince_core, and
camera/scalar/custom producers in lince_workflows. lince_camera holds the shared
capture driver used independently of the transport. ESP-IDF and component versions
are pinned. Driver dependencies, licenses and upstream references are included.
src/ contains the host validation, project, serial and installation pipeline.

Only ESP32-S3 is currently supported. The esp32s3 base profile assumes no PSRAM
or camera. The goouuu-esp32s3-cam-v1.5 profile describes the tested N16R8/OV2640
board, including its 8 MHz clock workaround. Other boards need verified profiles;
support for other ESP SoCs needs an adapter and tests, not just another chip name.

An export is an editable workspace, not the only authoritative firmware source.
Keep public customizations in this repository or a separately versioned project.
Never copy Wi-Fi credentials, device private keys, TLS private keys, enrollment
records, Cell snapshots or raw flash backups into the firmware source tree.
Keep generated build/ and managed_components/ out of Git. Firmware release
artifacts should record source revision, board profile, SDK and image hashes.

board.json selects hardware. cmake/board.cmake derives memory and camera SDK
settings at configuration time. Shared settings live in sdkconfig.defaults.
Generated SDK settings stay under build/; their filename depends on the profile,
defaults and dependency inputs. Edit the source inputs instead of generated
sdkconfig files. Camera pins are loaded into the native provisioning form and
must be confirmed separately. Destination/credentials remain provisioning data.

Validation order

Destination configuration uses a tagged destination object. Iroh is
{"transport":"iroh","endpoint_id":"<Cell EndpointId>"}; HTTPS is
{"transport":"https","origin":"https://cell.example","ca_pem":""}.
Audience, device, Signal and key_epoch remain separate setup fields. The iroh
camera frontend requires the camera workflow and verifies the provisioned Cell
identity before application authentication. Its configuration has no PC HTTPS
origin or certificate requirement. Native transport selection remains pending;
the existing native setup currently assembles the HTTPS choice.

The USB set_destination operation accepts {destination,setup}, preserves Wi-Fi
credentials/workflow in NVS, checks the physical provisioning window and restarts
after a successful save. Session::set_destination also pins the inspected P-256
public key. Nothing reads saved credentials back. Invalid updates preserve the
stored configuration; saving it cannot lower the retained trusted clock floor.
Session::begin_setup verifies the inspected key, opens the setup window through
the adapter's DTR/BOOT line and releases it on success, cancellation or failure.
Adapters without this wiring require holding BOOT on the running device. Native
setup exposes Open USB setup; configure/set_destination use the same operation.
Opening a serial adapter can reset the ESP before its first request is received.
Only hello is retried, every 500 ms within the original deadline, with the same
request ID. Configuration and destination writes are never automatically retried.
The host regression covers a dropped first hello and a single configuration
write; the same Rust begin_setup API opened this enrolled board's setup window
after inspection without changing its key or configuration.
From a terminal, cargo xtask ailuros set-destination <port> <public-key> reads
that nonsecret JSON object from stdin. It never needs a host password copy.

Run the isolated C configuration/storage fixtures with the actual SDK cJSON:

   nix develop .#ailuros-rust --command cargo test -p lince-ailuros --test configuration_host -- --ignored --nocapture

This uses simulated NVS and never opens a Cell or serial device. It checks
destination validation, credential/workflow preservation, refused updates,
retained previous destination fields, corrupt configuration and clock floors.

   nix develop .#ailuros-rust --command cargo test -p lince-ailuros --test identity_host -- --ignored --nocapture

The Linux host identity fixture uses the pinned SDK's actual Mbed TLS sources,
OS randomness and simulated NVS, rather than substituting cryptography. Thirteen
cases check first setup, preservation/signing with an existing key, matching
public markers, missing/truncated/invalid private keys, corrupt public markers
and interruption between public/private writes. Retained enrollment or iroh
entries forbid generating a replacement P-256 key. No physical NVS is touched.

The production Rust camera client's host tests live in iroh/tests/camera_client.rs.
Use RUSTUP_TOOLCHAIN=stable and an explicit desktop target when testing that
standalone manifest. They exercise authentication, demand, sixteen in-flight
frames, epochs/receipts, size/age drops and auth/ack/slow-reader deadlines.
The window permits 5 FPS with three-second receipts and stops capture at sixteen
unacknowledged frames or a separate 1 MiB payload budget, whichever fills first.
One receipt releases its frame and byte reservation. Each frame remains
capped at 128 KiB. Eight maximum-size frames fill the byte budget, while small
camera JPEGs can use all sixteen slots. The large-frame regression checks the
byte limit independently of frame count and verifies one-receipt recovery. Pending receipt
state retains metadata only. Camera demand, five-second freshness and existing
byte-rate, write and acknowledgment deadlines remain enforced.
An optional Camera::report hook receives five-second counters for capture
attempts, sends, receipts, full-window skips, rejected captures, pending receipts
and elapsed time awaiting capture/writes. These waits include runtime scheduling
and must not be presented as sensor-only timings. The device emits counters and
monotonic time over USB without retaining history or frame contents. Resource
samples read the SDK Wi-Fi power-save mode without changing it. The delayed-
receipt regression verifies 40 frames at 5 FPS and consistent interval counters.
Reports also include reserved payload bytes, summed/maximum receipt latency and oldest pending age,
measured with the monotonic clock independently of QUIC's path RTT.
The Rust camera's power-mode guard saves the current SDK Wi-Fi mode, selects
WIFI_PS_NONE for active capture, and restores the saved mode on close, failed
initialization and guard drop. Five host cases verify repeated cycles, all prior
modes, query/set failure, failed rollback and restoration retry. Check device
resource telemetry for the active/idle transitions during physical lifecycle
qualification; host policy tests alone do not prove camera throughput.
The network controller bridges ESP-IDF's station IPv4/route and link-event
generation into iroh. It replaces sockets after disconnect, address/route
changes or fast same-address rejoins while retaining the device secret. It
advertises the live IPv4 address and actual bound port with add_external_addr.
Five isolated host endpoint cases verify hint replacement/removal, stable
identity, invalid-address refusal, closed endpoints, constructor retries and
actual pinned transfer after socket recreation.
Publication polls link/clock readiness and stops capture before rebuilding a
changed endpoint. Hardware tests must verify direct routing and actual network
changes; the POSIX netwatch fallback cannot supply those observations itself.
The ESP adapter runs the shared camera on a separate bounded worker so capture
does not block the iroh runtime. Its driver and frame guards release SDK buffers.
Readiness tests reproduce ESP-IDF 5.5.2's consuming sntp_get_sync_status flag.
Remember a completed synchronization across repeated polls and Wi-Fi reconnects,
while still requiring connectivity and the retained clock floor. Requiring a new
COMPLETED value on every poll strands the camera before it can dial its Cell.
Production resource samples include monotonic milliseconds. SDK certificate
verifications taking at least 250 ms report their curve, duration and outcome,
without certificate bytes or key material. Compare these against frame age and
the fixture's observer/decode delays when investigating runtime stalls. The
current scheduling candidate polls timers/I/O and the global task queue after
each task poll; this remains subject to physical throughput qualification.
The provider reuses only successful byte-identical SDK signature calculations,
including curve/digest, public key, message and signature in each comparison.
It retains at most eight entries with 256..4096 message bytes, 97 public-key
bytes and 104 signature bytes each; short handshake proofs and oversized inputs
stay uncached. Failed results
never enter it. Rustls still checks chain, trust, hostname and validity time on
every connection. The warmed-chain regression tests name/time/trust/tamper
rejection after successful reuse. Resource samples include cache entries/hits/
misses. Selected-path telemetry includes RTT and packet losses; qualification
must measure transport delay, performance and bounded retention together.

   nix develop .#ailuros-rust --command cargo xtask ailuros compile-iroh-camera <project>
   nix develop .#ailuros-rust --command cargo test -p lince-ailuros --test iroh_sdk exported_iroh_camera_links -- --ignored --nocapture

The compiler records IrohCamera separately from IrohQualification, Workflow and
Tests. The SDK test exports a fresh project and links/validates images without
flashing. AILUROS_CAMERA_OUTPUT may select a new, nonexistent export directory.
SDK linking and host tests do not qualify actual ESP-to-Cell camera publication.

engine/tests/ailuros_camera_hardware.rs is an ignored physical qualification
fixture. It creates only an isolated in-memory Cell/Wire and requires explicit
AILUROS_DEVICE_PUBLIC_KEY, AILUROS_HARDWARE_PATH=internet|relay and a nonexistent
AILUROS_HARDWARE_OUTPUT directory. It emits destination.json for a trusted USB
update, then checks 170 decoded 320x240 JPEGs, a 4.5 FPS minimum against the
5 FPS target, capture age, two/one/zero/reopened viewers, clearing/epochs and
revocation/reauthentication. Its report contains metadata, never saved images.
FPS is asserted after all lifecycle stages so a slow candidate can still check
shutdown/reopening and revocation. A report with lifecycle_checked=true and
performance_ok=false is a failing qualification, even when all 170 frames were
decoded. Acceptance requires ok=true and the successful test exit status.
Capture-age, framing, image and authorization failures still fail immediately.
The internet choice permits direct/relay routing; it does not prove a direct
path without the ESP's path telemetry. The relay choice disables direct IP
transports on the receiver. An installed diagnostic does not pass this fixture.
Restore the intended persistent destination after an isolated hardware run.

The commands below are instructions, not an automatically executed setup.
Runtime installation and tests require the owner's authorization for that stage.
Authorization to test or flash a connected ESP does not authorize starting or
changing the production Cell service. Use isolated endpoints while that hold
remains. Diagnostic firmware is not a camera receiver or production workflow.

1. Static Rust checks and host tests

   nix develop .#interface --command cargo check -p lince-ailuros -p xtask --tests
   nix develop .#interface --command cargo test -p lince-ailuros

   Check profile validation, unknown profile rejection, source-preserving profile
   selection, symlink refusal, capacity/MAC checks, stale artifacts, mode-bound
   fingerprints, protected NVS ranges, cancellation and redacted serial errors.

2. CMake configuration tests, without ESP-IDF or hardware

   nix develop .#interface --command cargo test -p lince-ailuros --test board_configuration -- --ignored

   Requires CMake 3.19+. Check base -> GOOUUU -> custom quad-memory/clock -> base
   in the same workspace. SDK settings and configuration filename must follow
   each selection, including shared-default changes. Invalid clocks must fail.

3. Compile the real ESP-IDF matrix, without installing it

   nix develop .#interface --command cargo test -p lince-ailuros --test sdk_matrix -- --ignored --nocapture

   This executes the profile/mode and profile-switch matrix below and verifies
   the generated SDK settings, test flags and artifact images. It never flashes.

   nix develop .#interface --command cargo xtask ailuros profiles
   nix develop .#interface --command cargo xtask ailuros export /tmp/ailuros-validation/base esp32s3
   nix develop .#interface --command cargo xtask ailuros export /tmp/ailuros-validation/camera goouuu-esp32s3-cam-v1.5

   For each exported project:

   nix develop .#interface --command cargo xtask ailuros compile <project>
   nix develop .#interface --command cargo xtask ailuros compile-tests <project>
   nix develop .#interface --command cargo xtask ailuros compile <project>

   All SDK warnings are errors. Verify artifact.mode is workflow/tests/workflow.
   Verify LINCE_RUN_TESTS and LINCE_COMPILE_TESTS in build/CMakeCache.txt agree
   with each mode. In particular, a final normal compile must turn both OFF.
   Check generic firmware has PSRAM disabled and camera clock zero, while the
   GOOUUU profile enables octal PSRAM at 80 MHz and an 8 MHz camera clock.

   Switch one project through camera -> base -> camera using:

   nix develop .#interface --command cargo xtask ailuros select-profile <project> <profile-id>

   Compile each selection in the same build directory. Check the correct SDK
   file is selected and no previous memory/clock choices carry over. Compilation
   creates new source/image fingerprints; old artifact approval is invalid.
   This matrix passed on 2026-10-18 after the shared camera extraction. New
   transport or SDK changes still require the affected validation.

   Artifact flash_bytes records the SDK's declared flash capacity. Applications
   may grow beyond the original 4 MiB layout only within that declared capacity.
   NVS remains at 0x9000 with size 0x6000; ordinary installation never erases it.
   Installation checks both the board minimum and the artifact capacity against
   the physical chip before writing any image.

4. Native/backend checks, without opening the desktop app

   nix develop .#interface --command cargo check -p lince --features facade
   nix develop .#interface --command cargo test -p lince-interface --features native-media --lib -- ailuros_ui video_castle::tests
   nix develop .#interface --command cargo test -p engine --test signal_endpoints
   nix develop .#interface --command cargo test -p lince-facade --lib signal_streams

   Verify each native Create project button exports the selected profile. Loading
   a base profile after a camera profile must clear camera pins, confirmation and
   any previously compiled artifact. Confirm credentials remain transient.

5. Actual hardware stage, only after separate authorization

   Use a recoverable board with confirmed wiring and matching memory. Keep the
   expected MAC and public key explicit. Compile/install the tests artifact,
   read the ailuros-tests JSON result on UART at 115200 baud, then compile/install
   a workflow artifact. Confirm the public identity and provisioned connectivity
   survive ordinary updates. Do not erase NVS or regenerate identity to fix errors.
   Test base-profile refusal of camera provisioning on a spare/unconfigured board.

   With a separately authorized receiver running, use the lince-facade example
   ailuros_camera_check with explicit Cell directory, Signal UID and HTTPS origin.
   It starts a temporary headless Cell, so no other instance may own that directory.
   Check 150 decoded JPEG frames with two viewers, ten with one remaining viewer,
   final-viewer frame release/epoch change, then ten after reopening. Repeat after
   reboot and wall USB power. Validate actual Video Castle rendering separately.

6. Qualification beyond the first short stream

   Measure a long soak, memory use, frame age, bandwidth, dropped frames and power
   stability. Exercise receiver/network loss, invalid certificates and clocks.
   Design storage-write interruption tests on a spare board before deliberately
   corrupting storage or cutting power mid-write. Qualify every new sensor/profile.

Historical baseline

Before this refactor, the attached GOOUUU N16R8/OV2640 passed 15 device Unity
cases and 170 decoded 320x240 frames with viewer lifecycle on both computer USB
and wall power. That evidence establishes the profile's provenance; it does not
replace compilation, tests or hardware validation of the reorganized firmware.
