# Faster local compilation and finishing Park

Research and local implementation: 2026-10-29. The user authorized choosing and implementing the fastest working defaults. [Park.md](Park.md) remains the only Park acceptance plan, with three automatic workflows and two requiring the user. Build measurements and checks below are engineering verification, not additional Park acceptance subjects.

## Implemented defaults

The Nix development shells pin Rust 1.96.0, enable sccache with a persistent `target/sccache` cache and a 100 GB limit, retain incremental development builds, and use Clang with Wild 0.9.0 on x86_64 Linux. Cache-server idle shutdown is disabled and server errors go to `target/sccache/server.log`. Host-specific Cargo linker/flag variables preserve the Android target compiler; explicit environment overrides still win. `cargo_command` reuses an active Lince development shell. Park tasks no longer overwrite those flags just to deny warnings: owned packages already inherit the workspace's `warnings = "deny"` lint. Release builds retain their shipping optimization and unwind behavior.

`lince-park-clients` compiles the existing session and capture probe sources with their actual client dependencies. They no longer build as examples of the whole compositor. Their consumers and both CI helper recipes use development artifacts. The fixture runner also defaults to the existing development/test profile; release remains required for actual performance measurements and installed delivery. CI now saves compiled artifacts after helper compilation, including in the standalone helper workflow.

Nix's application source filter retains Cargo inputs, crate sources, assets and packaging, while excluding unrelated plans and runtime Records. Runtime content still has its separate `lince-content` derivation. Anicca's parser cache now identifies the actual generator executable and grammar instead of invalidating on every unrelated `Cargo.lock` change. Migration files and guards are unchanged.

The runner now exposes A1/A2/A3/B1/B2 and lets independent fixture subjects run before packaging, continues through independent fixture failures, and writes each result immediately to `fixtures.json`. It reuses a passed fixture only with matching executable and runtime/tool inputs and unchanged log evidence. Zero selected cases fail. Reports remain readable as historical evidence after source changes, and unrelated Records/plans are excluded from the source guard. The dispatch conversion and result ledgers are implemented and checked; desktop acceptance remains incomplete, and the immediate batch has stopped at the user's request.

Enter the development shell once for a series of iterations, then run Cargo/xtask inside it:

```sh
nix develop .#interface --option builders ''
cargo check --locked --keep-going -p lince-park --features session,server-tests,clipboard-gate --lib --timings
```

Keep `target` and the cache between runs. Do not start another build against that target while one holds its Cargo lock. Do not restart Nix, change toolchains, change flags or create another target directory for each fixture. Git-backed flake source acquisition can itself become noticeable while other work continually changes the checkout; an already active shell avoids repeating that work.

## What is actually delaying progress

Compilation is a substantial cost, but it does not explain the lack of completed results by itself. The original runner made scenario 01's package/capture/native preparation a prerequisite for every other subject, including independent fixtures. Its fixture loop returned on the first error, and its source guard hashed essentially every tracked/untracked non-Markdown file outside `target`, including unrelated Records. A later unrelated edit could invalidate a run or prevent opening its report. The implementation above removes these barriers for independent fixtures; the runner now implements the five-workflow orchestration in Park.md.

The existing final runner is in `crates/xtask/src/park/validation/final_suite.rs`; fixture compilation and execution are in `final_suite/scenarios.rs`. Fixture compilation previously requested the entire release `lince-park --lib` test executable with `session,server-tests,clipboard-gate`, even for a small selected list. Runtime selectors do not reduce what Rust must compile into that executable. Approximately 49,138 lines currently live in Park's `tests` files/directories; this is a scale indicator, not a measured attribution of release compile time.

The previous CI audit found one native application build lasting 36m06s followed by 59m04s of helpers, and another helper step lasting 88m02s, including 80m16s compiling release fixtures. `build.yml` previously saved its compiled cache before helpers; `park-validation.yml` restored it without saving the completed helper compilation. The independent native-probe workflow compiled its small helper in 20 seconds. Repeatedly rebuilding broad dependencies and restarting preparation was consuming hours before useful checks could run. Local work is now the primary iteration route; CI publication must not gate it.

The previous Nix source filter included nearly the whole checkout, so unrelated plan/Record edits changed the application source derivation. That filter is now narrowed. `buildRustPackage` still vendors dependency sources rather than caching compiled dependencies separately, and its source-package build cannot simply import the local Cargo target. A commit/revision change can also change embedded build identity. Prepare the installed package once after fixes stabilize; do not invoke that separate release build after every fixture.

Machine: Intel i7-1165G7, four physical cores/eight threads, 16 GiB RAM, Niri and ordinary desktop processes running. Nix interface shell: Rust/Cargo 1.96.0, LLVM 22.1.2. Existing caches were retained. These are practical local measurements, not an otherwise idle hardware benchmark. Do not compare their absolute durations directly with a different CI machine.

The small benchmark uses a copy of the actual `crates/park/examples/session_probe.rs`, with four direct dependencies and the same pinned versions as the repository. It compiles the full probe but executes only `--help`; it is a compiler experiment, not proof of Wayland behavior. Timed small edits change a help string in that copy, not production code. ## Architectural limits and future trimming

Prioritize the following review targets. Reducing lines or test count is a means, not the metric.

| Target | Concrete reduction | Why it is promising / limit |
| --- | --- | --- |
| Full dependency graphs for standalone probes | Compile client-only helpers independently with their actual dependencies. | Already supported by the local native-probe experiment; highest-confidence small change. |
| Repeated acceptance fixtures and matrices | Keep the representative Park.md paths and reported-bug regressions; remove duplicate size/orientation/provider sweeps from the selected gate. Consolidate duplicated setup. | Cuts runtime/restarts immediately. Compilation savings require actual code/module/dependency removal, not merely a name filter. |
| Shared test helpers and generic fixture bodies | Replace repeated large bodies with one shared implementation and small data cases where they test the same behavior. Avoid needless generic monomorphizations. | Can reduce codegen/linking; retain distinct assertions for real different behaviors. Measure rather than promise. |
| `interface` → `cell`/`engine` coupling | Inspect whether host-control/policy models and pure logic can depend on a small existing contract instead of the whole application service graph. | These crates dominate the observed check. A broad engine refactor is not required to finish Park; choose a small boundary only if it removes real dependencies. |
| Unnecessary Cargo features / duplicate crate versions | Inspect `cargo tree -e features` and `cargo tree -d` for the selected artifact; remove actually unused features and align compatible versions. | `engine` and `cell` already have empty default features. Adding `default-features = false` cannot remove their unconditional dependencies. Preserve Sandbox and Park's existing media/map/GLB/WGSL functionality. |
| Source-scanning build scripts | Inspect `sensei::teach` watchers and generation inputs; narrow unnecessary reruns and avoid rewriting unchanged generated output. | It watches source/tests/examples; edits can propagate. The measured dominant costs were Rust units, so do not assume scanning is the main bottleneck or bypass its rules. |
| Test-only dependencies on broad packages | Check Park's unconditional dev-dependencies, including `store`, against retained fixture needs before extracting or removing them. | A dependency disappears from compilation only if no selected target/feature still needs it. |

A concrete remaining coupling is `crates/nucleus/build.rs` fingerprinting engine/store/protein sources, and `crates/simulation/build.rs` fingerprinting Cell/engine and other sources. Both also include the root manifest and lockfile. An edit in a consumer can therefore invalidate shared dependencies, not only that consumer. These hashes protect cached execution/provenance; removing their inputs merely to suppress rebuilding would be wrong. A future boundary change should preserve the actual build identity while moving its computation out of widely shared crates. This is a larger architecture task, not another Park acceptance prerequisite.

A five-second CPU sample during the local simulation compilation observed Rust type interning, MIR-to-LLVM generation and monomorphization/normalization work. This was a bounded sample, not an attribution of the entire build, but it rules out treating all current delay as linking. The original `simulation-perf.data` was lost with the target directory; this is a historical observation.

For future recurring Fiote reviews, use the existing trail mechanism when scheduled by the user; no new agent scheduler or automatic deletions are part of this task. Each proposal should identify the duplicate/unused behavior, the dependency or compile unit it removes, a before/after timing from the same recipe, and the remaining observable check that protects the behavior. Prefer one measurable simplification per iteration. Do not generate replacement coverage for every deleted test or remove input/privacy/persistence protections just to lower a number. Do not alter existing migrations or migration guards.

## Compiler/linker options considered

These are alternatives to evaluate selectively, not a new mandatory benchmark matrix or additional Park acceptance work. A full application comparison is justified only when the relevant compile stage is expensive. Stop investigating an option that fails its bounded compatibility trial and proceed with the working stable toolchain.

| Option | Decision |
| --- | --- |
| Blaze | Tested and currently blocked on the standard library panic path with both shipped backends. Do not make Park depend on it. It owns its Rust toolchain and upstream recommends normal Cargo/CI as final authority. Revisit a release fixing the observed failure; do not project its advertised speedups onto Lince. [Blaze](https://github.com/indexable-inc/blaze), [Cargo/toolchain behavior](https://github.com/indexable-inc/blaze/blob/main/docs/cargo.md) |
| Official rustc Cranelift backend | Potentially useful for unoptimized edit/run loops. Not benchmarked here. It keeps rustc's frontend but changes code generation; upstream lists partial `std::arch` support and experimental unwinding, with abort enabled by default. Park uses unwind/recovery behavior, so it cannot silently replace the final compiler or supply release FPS evidence. Use a pinned compatible nightly and an isolated target only for a bounded compatibility trial. [Cranelift backend](https://github.com/rust-lang/rustc_codegen_cranelift/blob/master/Readme.md) |
| Faster linker: LLD/mold/Wild | The initial small-probe comparison was overridden by user Cargo flags and has been withdrawn. Corrected replay of the same full Park fixture link took 30.115 s with LLD, 16.194 s with mold and 10.487 s with Wild 0.9.0. All three linked and executed `--list` successfully. This is one measured round, not a three-round median or an end-to-end compilation speedup. Wild is the local x86_64 Linux default; the fresh full-size build verifies it again. Wild currently performs full linking; incremental linking is planned, not delivered. Do not claim an incremental-link win. [Wild](https://github.com/wild-linker/wild), [mold](https://github.com/rui314/mold) |
| Bevy dynamic linking in development | Worth a full-app relink experiment only if linking dominates; keeps dependency code in a reusable dynamic library. Does not remove frontend/type-check work and creates another feature/artifact variant. Never ship the development dylib arrangement as the installed package by accident. Not benchmarked here. [Bevy setup](https://bevy.org/learn/quick-start/getting-started/setup/) |
| Parallel compiler frontend | Different from Cargo's parallel crate jobs. Current upstream documents `--jobs-frontend` in place of old `-Zthreads`; availability is compiler-version dependent. The pinned 1.96.0 help does not expose the newer interface. Check the exact compiler before trying it, use a pinned experimental compiler if needed, and avoid `RUSTC_BOOTSTRAP` or oversubscribing every crate. Not benchmarked on Park. [rustc parallelism](https://doc.rust-lang.org/rustc/command-line-arguments.html#-j--jobs---jobs-frontend---jobs-backend---jobs-linker-limit-parallelism), [old threads flag](https://doc.rust-lang.org/nightly/unstable-book/compiler-flags/threads.html) |
| `hint-mostly-unused` | Possible selective codegen reduction for a large binding/API crate used narrowly. Do not apply globally: upstream warns that mostly-used and generic-heavy crates can get slower. Check compiler support and per-crate timings before a trial. Not benchmarked here. [Rust's guidance](https://blog.rust-lang.org/inside-rust/2025/07/15/call-for-testing-hint-mostly-unused/) |
| Profile tuning | Existing dev settings are already compilation-oriented. Low optimization helped edited probe builds; optimize runtime-critical dependencies only as needed. Higher release codegen-unit counts or incremental release may help iteration but need a real-app comparison, including resulting runtime. Cross-crate LTO is already not enabled; default local ThinLTO is a separate consideration. PGO/BOLT, full LTO and one codegen unit prioritize runtime rather than the current iteration goal. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) |
| More jobs, memory, RAM disks, cache size | Four versus eight jobs was essentially a small-workload tie. The laptop has four physical cores and 16 GiB RAM; unlimited concurrency can cause swapping and lengthen builds despite abundant swap space. Keep disk caches; do not put the whole target in tmpfs at the expense of compiler memory. Measure memory pressure and wall time, not just CPU utilization. Larger caches help only by avoiding actual eviction. |
| Newer rustc, distributed builds, alternate build systems | Compiler upgrades can help but invalidate artifacts and need a compatibility trial; changing version repeatedly loses the cache benefit. Distributed builds need other machines and conflict with a local-first immediate solution. Replacing Cargo/Nix with Bazel/Buck or adding Docker/cargo-chef is not warranted to finish Park. No external build service is required. |

Blaze's affected-test caching also does not automatically solve Park's reuse policy: its documented retained passes depend on sandboxed/hermetic execution, whereas compositor tests intentionally use host graphics, Wayland and sometimes session buses. Keep real dependency-aware artifact evidence rather than assuming a compiler cache certifies those interactions. [Blaze test caching and sandboxing](https://github.com/indexable-inc/blaze/blob/main/docs/cargo.md)

## How to judge whether a change paid off

Separate shell/setup time, dependency compilation, changed-crate frontend/codegen, final linking, fixture startup and actual test execution. Save `--timings` output and compare the same source edit, toolchain/features/profile and hardware load; record three edited rebuilds and their median. For large builds, capture real compiler/linker phase data before choosing a linker optimization. Do not sum overlapping unit durations. [Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html)

A successful iteration improvement means fewer unnecessary rebuilt units, shorter edit-to-first-result time and more independent results collected per pass. A useful policy for optional changes is a repeatable material gain on the relevant full-app stage, without a regression in required functionality; a tiny helper speed difference is insufficient evidence for a global change. Reaching five passed Park workflows is the delivery objective. Compiler experiments stop being productive when they delay that objective more than the remaining builds would cost.
