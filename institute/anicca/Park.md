## Flake-centric NixOS setup

No nixpkgs registration or upstream NixOS module is required. The repository already exports `nixosModules.park`; importing it makes this repository's `programs.lince-park` options available locally. With the Lince flake already provided as `inputs.lince`, the basic login registration is:

```nix
{ inputs, ... }:
{
  imports = [ inputs.lince.nixosModules.park ];
  programs.lince-park.enable = true;
}
```

This existing module adds the package and Wayland session to the current display manager. It does not choose a new default session or remove Niri. It assumes a display manager is already configured, as in the user's current setup.

During development, explicitly choose the source package when the flake's published binary is older than the code being tested:

```nix
{ inputs, pkgs, ... }:
{
  imports = [ inputs.lince.nixosModules.park ];
  programs.lince-park = {
    enable = true;
    package = inputs.lince.packages.${pkgs.stdenv.hostPlatform.system}.lince-ui-source;
  };
}
```

The `lince` input must point to the intended revision/source. Once the tested binary is published and selected by the flake, the package override can be omitted. Merely importing a GitHub input does not include uncommitted local work.

**Current integration detail:** the existing module registers a plain Park session; it does not automatically configure UWSM or its readiness command. Test 01 owns that small remaining binding and its validation. The desired final consumer setup stays the simple import plus enable, with UWSM handled by the flake module and the existing post-interactive-frame readiness path. Do not add a second service manager or make the user maintain custom session scripts. Upstream [UWSM's readiness documentation](https://github.com/Vladimir-csp/uwsm#2-service-startup-notification-and-vars-set-by-compositor) describes the required finalization handoff; NixOS already supplies the external `programs.uwsm` integration.

No personal NixOS configuration, flake lock, host service environment, greeter activation, publishing or running session is changed by this plan update. Implementation/execution of the fixed suite and any necessary binding fixes proceed when requested; host activation and physical/login observations remain scheduled with the user.
