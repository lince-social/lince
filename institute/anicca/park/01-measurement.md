# 1. Measure complete interactions

[Organization and execution order](Park.md). Targets are in [benchmarks](08-benchmarks.md); interaction coverage is in [workflows](09-workflows.md).

Measure command-to-effect latency first, including native typing and local Record saving. Existing counters/timing histograms and the private renderer fixtures are reusable; add only the missing causal links. An observation of high CPU or a stage's elapsed duration is not attribution of user-visible delay. P103 completed the [fixture definition](workloads.json) and current runtime/source identity manifest; P101 has added and checked native/client correlation; trace local edit/save phases next, then rank causes. Mixed-scene adapters and actual daily counts are explicitly still pending under their implementation/inventory tasks. The same trace serves scheduling, storage, style and GPU questions.

- [ ] **P102 — Trace one local Record edit through durability and view publication.**

    **Why:** a title/description save currently has several possible amplification and wait boundaries. **Scope:** on a private synthetic local Record, correlate editor revision, draft preparation/encoding, draft-write queue/acquire/commit, ChangeRecord admission, access scope, canonical transaction, acknowledgement, query/collaboration refresh, affected-view update and visible presentation. Count SQL statements, transaction/fsync boundaries where observable, snapshots/bytes, clones, query executions and views touched. Measure head and body separately at 1 KiB/64 KiB/1 MiB body sizes and one versus eight views. **Close with:** a critical-path/work-amplification report distinguishing immediate echo, durable recovery, canonical save, publication and remote sync, with no network dependency on the local baseline. A blocked writer scenario is a correctness probe, not the normal latency result. **Feeds:** stage 3; use actual file-backed storage for durability costs.

    **Implemented and checked so far:** existing opt-in reporting now separates native binding updates, edit splicing, recovery encoding, storage task queue wait, awaited draft writes, local ChangeRecord service and view publication, with bounded counters for snapshot/encoded bytes, writes/clears and views. Private file-backed WAL/Full fixtures completed title/body edits at 1 KiB and 64 KiB with one/eight views; tracing-off controls and exact database reopen checks passed. Cleanup no longer encodes a snapshot that it immediately discards, and selection reuses the already-read current editor text. Evidence: 00 and target/park-validation/performance-20261105/local-edits/.

    **New evidence:** all eight empty/1 MiB, title/body, one/eight-view file-backed cases now complete with exact cold reopen. Reusing the isolated locally authored candidate removes the duplicate JSON import during large text preparation. Checkpointing a mutation with at least 65,536 new operation atoms removes the reproduced large-tail reopen stall without deleting history or relaxing guards. The four 1 MiB fixtures completed in 8.2–9.7 seconds each, including setup, three edits and reopen; the earlier preparation and reopen attempts each exceeded 180 seconds. These are diagnostic runs with different intermediate implementations, not optimized desktop speedup ratios. At that stage, tiny title edits alongside the large body spent roughly 80–100 ms preparing foreground recovery snapshots. The completed incremental recovery work in 00 removes that repeated cost; normal three-edit cases now export zero full recovery snapshots and three binary updates totaling under 300 bytes.

    **Still required:** per-edit causal linkage through the now-instrumented gate/transaction/reaction/query phases, populated Protein-query fanout, causal presentation and actual SQL/fsync counts where observable. CreateRecord has a separate 256 KiB body limit; larger setup uses the supported text-edit API without changing guards. The high-entropy diagnostic body differs from the frozen S4 paragraph recipe; the complete S4 adapter remains pending. Native timings include bounded polling and ordinary desktop drift, so no end-to-end speedup is established. Broader snapshot/replication checks and P123's borrowed-editor work are now locally verified in 00. Incremental recovery is complete, including actual private-process unclean-exit checks at four durability boundaries. Canonical acknowledgement and large-body splicing remain slow in the diagnostic; finish their missing causal breakdown without delaying already-supported work removal such as the concrete P79 candidate.

    **Backend phase reporting implemented and checked:** a small opt-in hook feeds the existing reporter from engine/transport code. It times access/import gate waits and held scopes, admission, accepted-document lookup, complete-history validation/encoding, candidate import/build, snapshot/delta export, canonical begin/body/commit, observation/reactions and query execution/refresh. Only declared static labels and numeric readings are forwarded. Source checks and observer/privacy tests pass without warnings; 46 guards, 20 native binding cases, five reporter checks, four transport cases and the common interface suite pass. The stale invisible-Record test now explicitly restricts visibility to an owner while preserving denial and local-access assertions; production permissions are unchanged. Identified baselines/failures are in target/park-validation/performance-20261105/backend-phases/; final sources, executables and 22 exact-reopen measurements are in accepted-history/receipt.json beside it. The repeated base-history validation was removed under P137, halving full-history checks/encoded bytes; body acknowledgement controls remain mixed, so an optimized desktop latency win is unproven. Awaited scopes overlap; begin includes pool/BEGIN/commit-sequence work, global gate/query readings lack per-operation causal identity, and these do not observe hardware CPU time, individual SQL/fsync execution or physical pixels. The text-only fixture does not establish populated Protein-query fanout. Keep P102 open for those missing links and coverage; reuse these signals rather than building another profiler.
