Currently in SQLite. We have a Rust macro for diffing the current db with a cached one for generating migrations automatically. This was done mainly in the process of making the database schema be defined by rust structs. It is possible to write sql for the migrations by hand and change the struct before running for changes that the macro can't catch (columns changing names and such). The migrations are run before the app really starts.

We have a system of one writer many readers, functions shouldn't query the db directly, they should ask the single writer to run the query, that way we appease the SQLite model, dont have problems with pooling and can do some pretty fun stuff for the many readers part.

I believe that for every View streaming data to HTTP endpoins, or other interfaces, we have a reader of the data, whenever a Record what is selected by the View changes, we hydrate all the connections through SSE that are listening to those Views. This was vibe coded just to test, and we need to clean it up. Maybe we should make the SSE be against Rust data in memory, and the Views stream data to the memory of the backend, that way we dont have to open many requests in sql and can do it in Rust if it's a problem in the future.
